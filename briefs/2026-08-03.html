Topology-Aware Data Movement for Disaggregated GPU Inference

Authors & affiliations: Sanjeev Rao Ganjihal. Affiliations: Independent Researcher.

Tags: LLM Serving, Topology-Aware KV Transfer, GPU Fabrics

Problem: Prefill/decode disaggregation turns KV cache movement into a recurring high-bandwidth network problem. The paper argues that treating all transfers as uniform RDMA misses huge bandwidth differences across NVLink, InfiniBand, and TCP paths.

Key contributions from the authors:

  • Designs a topology-aware transfer orchestrator that discovers interconnect hierarchy and chooses the transfer path per source/destination pair.
  • Combines layer-by-layer pipelined transfer, cache-aware decode placement, and adaptive fallback when fast paths are saturated or unavailable.
  • Quantifies the stakes with 70B-class KV transfers: multi-GB per request and more than 100 GB/s aggregate movement at production rates.

Why it matters: This is the strongest signal today because it states the systems problem cleanly: disaggregated inference is not just a scheduler problem; it is a topology-sensitive data-movement problem.

Key insights:

  • Uniform RDMA is a leaky abstraction when GPU pairs can differ by orders of magnitude in achievable bandwidth.
  • KV placement and decode-worker placement should be coupled; otherwise the scheduler can create avoidable cross-domain traffic.
  • Layer-granular pipelining is a useful mental model: transfer should overlap with decode consumption instead of waiting for the full KV object.
  • The paper is more vision/design than production evaluation, but the architectural framing is directly relevant to superpod serving design.

Actionable lessons: Expose topology class, path bandwidth, and transfer congestion to the inference scheduler. Treat KV movement as a selectable data plane—NVLink/NVSwitch, RDMA/IB, Ethernet/TCP, or storage-backed paths—not as an opaque runtime copy. For production, validate the policy under churn: cache hits, failures, and decode pool load matter as much as raw link speed.

Useful diagram: No obvious architecture diagram was found in the PDF text; the paper is mostly a conceptual design and argument.

X-Stage: An Overlooked Pipeline Stage for Communication-Computation Overlap in DiT Inference

Authors & affiliations: Jianwen Xian, Zhiyuan Xu, Yuchen Li, Ziliang Lai, Kang He, Zhen Huang, Aichen Feng, Jinyan Chen, Yilin Zhang, Qinqin Chen, and Chengru Song. Affiliations: KlingAI Research; Tsinghua University; NVIDIA.

Tags: GPU Communication, Compute/Communication Overlap, Distributed Inference

Problem: Fine-grained device-initiated remote stores can overlap communication with Tensor Core work, but sender-side post-issue progress creates hidden backpressure that existing overlap schedulers do not model.

Key contributions from the authors:

  • Identifies X-Stage: a software-visible post-issue stage between issuing a remote store and remote-visible completion.
  • Builds a lightweight Burst–Gap model using issue time, effective drain rate, and outstanding-capacity limits to predict sender backpressure.
  • Uses the model to redesign fused kernels for DeepGEMM MegaMoE and Ulysses-style sequence-parallel attention, reporting up to 1.62× MegaMoE kernel speedup and up to 1.33× FlashAttention-4 speedup in evaluated cases.

Why it matters: This is useful because it exposes a microarchitectural communication pipeline stage that can silently defeat “overlap communication with compute” assumptions.

Key insights:

  • Overlap is not binary. A remote store may be issued, but finite outstanding capacity still couples future communication to current compute scheduling.
  • For MoE and sequence parallelism, burst shape matters: spreading remote-store bursts across useful compute can reduce sender-visible stalls.
  • The right abstraction is not only “when is data needed by the receiver,” but also “when does the sender recover injection capacity.”
  • Device-initiated communication needs performance models that include drain and recovery, not just launch overhead or link bandwidth.

Actionable lessons: When designing fused communication kernels, profile the sender-side issue span and residual backpressure, not only receiver wait time. Insert compute in the gaps where it helps drain outstanding remote stores. For collective/runtime design, expose backpressure signals so schedulers can avoid concentrated injection bursts.

Gleam: Adaptive Network-Efficient CUDA API Remoting for Cross-Device GPU Sharing over LANs

Authors & affiliations: Zhihao Xu, Hao Zhong, Zeting Zhou, Yuhang Xu, Haoyu Tong, Wei Wang, Jinshan Chen, Keqiang He, Chong Zhu, Shengzhong Liu, Fan Wu, and Guihai Chen. Affiliations: Shanghai Jiao Tong University; Lenovo Information Products (Shenzhen) Ltd.; Lenovo (Beijing) Ltd..

Tags: GPU Sharing, CUDA Remoting, LAN Networking

Problem: CUDA API remoting can share remote GPUs across LAN devices, but bandwidth overhead, frequent API calls, and cross-task contention make the network—not raw GPU compute—the bottleneck.

Key contributions from the authors:

  • Introduces Gleam, a task-generic GPU sharing framework built around network-efficient CUDA API remoting.
  • Reduces transfer overhead with automatic model-weight caching and mitigates API-call latency via asynchronous execution.
  • Adds a path manager and adaptive network-aware execution mechanisms for contention among heterogeneous local tasks.

Why it matters: This is not superpod-scale, but it is a concrete reminder that GPU disaggregation over ordinary networks quickly becomes a control problem over bytes, calls, and contention.

Key insights:

  • API remoting amplifies small-message and control-path overhead; frequent CUDA calls can dominate even when bulk data is cached.
  • Weight caching is a network optimization as much as a memory optimization, because repeated model movement is often the avoidable elephant flow.
  • LAN GPU sharing has the same shape as larger disaggregation problems: placement, cache locality, and network contention have to be solved together.
  • The framework’s path-manager idea maps cleanly to larger systems that need to choose between local, rack-local, and remote accelerators.

Actionable lessons: For GPU pooling, measure the control plane: API-call rate, synchronization frequency, and cache invalidation traffic. Cache weights or reusable tensors near the serving GPU, batch/remap API calls where possible, and make the network path manager aware of concurrent tasks rather than treating remote GPUs as interchangeable.

REPS: Recycled Entropy Packet Spraying for Adaptive Load Balancing and Failure Mitigation

Authors & affiliations: Tommaso Bonato, Abdul Kabbani, Ahmad Ghalayini, Michael Papamichael, Mohammad Dohadwala, Lukas Gianinazzi, Mikhail Khalilov, Elias Achermann, Daniele De Sensi, and Torsten Hoefler. Affiliations: ETH Zürich; Microsoft; Sapienza University of Rome.

Tags: Datacenter Load Balancing, Packet Spraying, AI Training Fabrics

Problem: ECMP and oblivious packet spraying struggle to maintain high utilization and recover quickly under failures in large Ethernet datacenters, including AI-training traffic with heavy collectives.

Key contributions from the authors:

  • Proposes REPS, a decentralized per-packet adaptive load-balancing scheme that caches good-performing paths and recycles entropy.
  • Targets next-generation out-of-order transports such as Ultra Ethernet while keeping per-connection state below 25 bytes regardless of topology size.
  • Evaluates REPS with large-scale simulations and FPGA-based NICs, including AI collective traffic, and reports sub-100 μs rerouting away from failures.

Why it matters: This is older than today’s fresh window but still highly relevant: it attacks the exact failure/load-balancing layer that AI Ethernet fabrics are trying to harden.

Key insights:

  • The important move is adaptive packet spraying without centralized control; path quality is learned and reused close to the sender.
  • Fast failure reaction matters because AI collectives can convert one degraded path into cluster-wide tail latency.
  • The small state target is operationally meaningful for NIC implementation at many-flow scale.
  • REPS assumes/benefits from out-of-order tolerant transports, which aligns with the design direction of UEC-style fabrics but changes host/NIC reassembly expectations.

Actionable lessons: If adopting packet spraying for AI fabrics, co-design it with the transport’s reordering tolerance and NIC state budget. Test against collective patterns, not just synthetic incast/permutation. Treat failure recovery time as a first-class metric alongside average utilization.

CAPS: Fine-Tuning CCA Timing

Authors & affiliations: Raphael Zailer and Isaac Keslassy. Affiliations: Technion; UC Berkeley.

Tags: Congestion Control, Packet Timing, Datacenter Transport

Problem: Modern CCAs can converge to feasible rates while still leaving standing queues. CAPS separates rate allocation from packet timing and tries to phase-lock senders to bottleneck slots.

Key contributions from the authors:

  • Introduces Clocked ACK-Paced Synchronization, a lightweight scheduling layer that adds delay correction on top of ACK-clocking.
  • Shows that if flows reuse assigned bottleneck slots across frames, queues can drop toward zero while maintaining high utilization.
  • Evaluates CAPS on all-to-one, permutation, and all-to-all datacenter traffic patterns.

Why it matters: CAPS is interesting for Ethan because it frames congestion control as a timing/phase problem after rates are stable, which is very close to the “phantom queue vs. actual queue” design intuition in low-latency fabrics.

Key insights:

  • Rate fairness is not enough; two flows with feasible rates can still collide in time and create queues.
  • Heterogeneous RTTs break naïve ACK-clocking because shorter RTT flows regain phase earlier.
  • The scheme is attractive as a shim over existing allocators, but deployment would need careful interaction with pacing hardware and NIC timestamping.
  • All-to-all evaluation makes it more relevant to collective-like traffic than a pure web-service CCA paper.

Actionable lessons: When evaluating datacenter CCAs, separate “rate convergence” from “packet arrival phase at the bottleneck.” Measure queue occupancy and phase drift under heterogeneous RTTs. If implementing timing correction, verify that NIC pacing granularity and clock stability are sufficient before trusting simulator-level results.
