Daily brief · 2026-05-17

AI cluster networking & infrastructure brief

Today’s brief is centered on KVCache as a first-class distributed systems resource: the main paper argues that long-context LLM serving should be scheduled around memory reuse and cache movement, not just GPU batching.

Most important paper of the day

Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

Authors & affiliations: Ruoyu Qin, Zheming Li, Weiran He, Mingxing Zhang, Yongwei Wu, Weimin Zheng, Xinran Xu (Moonshot AI / Tsinghua University).

Tags: LLM serving, KVCache, disaggregation, long-context inference

Why this is the top pick: It reframes long-context LLM serving as a distributed cache orchestration problem rather than a GPU scheduling problem, which is exactly the right abstraction boundary for modern prefix-reuse-heavy workloads.

Deeper explanation: Mooncake’s core move is to make KVCache the center of the serving architecture. Instead of treating prefill and decode as just two GPU phases to be colocated or loosely split, the system builds a dedicated distributed KVCache pool from CPU memory and SSD attached to GPU servers, then schedules requests around reuse, placement, movement, replication, and eviction of those blocks. The Conductor scheduler is doing something more interesting than ordinary model-serving dispatch: it is deciding whether a request should exploit prefix reuse, whether fetching that cache will still satisfy TTFT, whether hot blocks should be replicated, and whether a request should be rejected early when the system is too overloaded to finish it within SLO. This matters for AI clusters because as context lengths grow, useful performance is increasingly dominated by memory hierarchy behavior and networked cache logistics, not just pure accelerator throughput.

  • Problem: long-context serving makes KVCache too expensive to recompute or fit naively in VRAM, while prefill and decode have different latency/throughput needs.
  • Key contributions: (1) a KVCache-centric disaggregated serving architecture, (2) a global scheduler called Conductor for cache-aware request placement and overload handling, and (3) chunked pipeline parallelism to reduce TTFT for long prompts.
  • Why it matters architecturally: it treats cache movement and reuse as the real control-plane problem in LLM serving.
  • Useful diagram: the high-level architecture showing prefill pool, decoding pool, KVCache pool, Messenger, and Conductor is the one to study first.
Published 2024-07-01 · LLM serving / KVCache / disaggregation

Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

Authors & affiliations: Ruoyu Qin, Zheming Li, Weiran He, Mingxing Zhang, Yongwei Wu, Weimin Zheng, Xinran Xu (Moonshot AI / Tsinghua University)

Tags: long-context inference, prefix reuse, distributed cache pool

Problem: Long-context LLM serving is increasingly bottlenecked by KVCache capacity and movement, while prefill and decode want different resource profiles and latency trade-offs.

Key contributions: (1) separates serving into prefill pool, decoding pool, and distributed KVCache pool; (2) introduces Conductor for cache-aware scheduling, replication, swapping, and early rejection under overload; (3) proposes chunked pipeline parallelism and layer-wise KV streaming to reduce TTFT for long prompts.

Why it matters: The paper pushes the community toward the right systems abstraction: long-context LLM serving is a memory hierarchy and cache orchestration problem layered on top of accelerator inference.

  • Prefix reuse is only useful if the scheduler can exploit it without breaking TTFT and TBT SLOs.
  • Distributed KVCache changes serving economics by turning underused CPU/DRAM/SSD resources into a near-GPU memory tier.
  • Overload handling matters: early rejection can improve goodput if doomed requests would otherwise waste GPU time.
  • Hot KV blocks behave like a skewed cache workload, which justifies explicit replication strategies.
  • The architecture is especially relevant for real-world MaaS systems with long prompts and repeated prefixes.

Actionable lessons: Treat KV reuse as a scheduling signal, not just a cache hit statistic; separate prefill and decode resource pools when their objectives diverge; and optimize for SLO-qualified goodput rather than raw utilization.

Useful diagram: The system overview showing Conductor, Messenger, and the three serving pools is the best entry point because it clarifies how disaggregation is coordinated.

Fast take

The big idea today is that long-context serving is becoming a cache logistics problem: whoever controls KV placement, reuse, and transfer controls throughput.
