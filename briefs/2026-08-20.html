When Does Distributed AI Inference Need More Wide-Area Bandwidth? A Co-Design Evaluation of Optical, Packet, and Software Levers

Authors & affiliations: Prasanna C. Prasanna C — Lightstorm.

Tags: AI Inference Networking, WAN/Optical Capacity, KV-State Transfer

Problem: Cross-site AI inference needs a principled answer to when moving inference state over a WAN is better than recomputing it, compressing it, routing around it, or simply overprovisioning packet capacity.

Key contributions from the authors:

  • Derives a workload model for transfer-versus-recompute decisions, including KV size, context length, attention architecture, concurrency, queueing, locality, loss, and jitter.
  • Estimates a crossover of 74–111 Gbps per active stream for a 70B multi-head-attention model, falling to roughly 9–14 Gbps under grouped-query attention at 1/8 KV heads.
  • Frames packet and optical levers as complementary: packet fabrics allocate lit capacity at millisecond timescales, while optical fungibility changes the amount of lit capacity at minute timescales.

Why it matters: This is the most directly network-facing paper in today’s set: it treats distributed inference as a bandwidth, tail-latency, and economics co-design problem rather than assuming “more WAN” is automatically the answer.

Key insights:

  • Attention architecture can move the bandwidth breakeven by an order of magnitude; GQA makes state transfer far more plausible than vanilla MHA.
  • Locality-aware routing and prefix/session stickiness are first-order network reducers, not minor serving tricks, because demand scales with the fraction of state that actually crosses sites.
  • The paper separates per-stream feasibility from aggregate capacity: one stream may fit, while many concurrent long-context sessions still collapse under tail jitter or loss.
  • Optical capacity is positioned as economic substitution for packet overprovisioning, not as a packet scheduler replacement.

Actionable lessons: For any cross-region or cross-campus inference design, model KV movement against recomputation with attention architecture, locality hit rate, and tail effective bandwidth in the loop. Do not evaluate WAN capacity using only mean throughput; include jitter/loss-induced goodput collapse and concurrency-driven queueing.

Q-First: Most of Attention Needs Only the Query in Disaggregated LLM Decoding

Authors & affiliations: WenJie Fan. WenJie Fan — Yotta Labs; email also lists USTC mail.

Tags: Disaggregated LLM Serving, KV Cache, Compute/Communication Overlap

Problem: Disaggregated decoding separates KV-cache sweeps from projection/feed-forward work, but the normal decoder ordering makes the memory-side and compute-side devices wait on each other within the same sequence.

Key contributions from the authors:

  • Observes that for a decode step with j context positions, j−1 cached attention terms can start from the query alone; the current key/value update can follow as a non-blocking cache write.
  • Defines a Q-First protocol that swaps sub-layer order to expose the query while compute-side work continues, using stock kernels and unchanged tensor shapes.
  • Validates the protocol on trained checkpoints and reports small relative error / loss movement, plus fine-tuning experiments for moving an existing checkpoint toward the required read point.

Why it matters: For disaggregated serving, this is a neat dependency-graph paper: it tries to create overlap by changing where the model reads the query rather than by adding more in-flight sequences and more resident KV cache.

Key insights:

  • The bottleneck is not only data volume; it is the decoder block’s ordering constraint between cache-side memory sweep and compute-side feed-forward.
  • Overlap gained by sequence multiplexing consumes exactly the resource disaggregation is trying to save — resident KV state — so dependency removal is attractive.
  • The “query-only” observation is narrow but powerful: most of the attention computation can begin before the current token’s K/V write is needed.
  • The paper is careful about bounds: pushing queries all the way from network input is measurably worse, so the win depends on a specific read-point shift, not arbitrary reordering.

Actionable lessons: When designing attention/FFN-disaggregated systems, draw the token-level dependency graph before adding queues. If a stage only needs Q to begin, keep K/V writeback off the critical path and measure overlap at TTFT/ITL level, not only kernel runtime.

Useful diagram: The paper does not have a big hardware architecture block diagram in the extracted text, but Figures 1–3 are useful for understanding training/equivalence behavior and the protocol’s measured loss/error envelope.

Pre-Compiled Pipeline Shards for Distributed LLM Inference on Intel AI PC Fleets

Authors & affiliations: Tate Berenbaum and Muthaiah Venkatachalam. Tate Berenbaum — Not Community Labs Inc.; Muthaiah Venkatachalam — Intel Corporation.

Tags: Distributed LLM Inference, Pipeline Parallelism, Edge/Client Fleets

Problem: A single AI PC cannot hold a large model such as a 70B LLM, but many idle client machines have enough aggregate memory and compute if the model can be split and coordinated over an ordinary network.

Key contributions from the authors:

  • Splits models by layer into pre-compiled INT4 OpenVINO graph shards, with each machine running one pipeline stage and passing activations to the next over a TCP relay.
  • Restores lost OpenVINO performance by injecting a beam_idx Gather into each shard, triggering IndirectKVCache fusion and bringing sharded execution closer to monolithic performance.
  • Adapts speculative decoding for stateful OpenVINO models by masking rejected draft tokens through attention_mask instead of physically trimming KV cache.
  • Demonstrates two-node Llama 3.1 8B concurrent serving and a four-node 70B deployment on Lunar Lake AI PCs at interactive speed, with code and logs released.

Why it matters: This is not superpod networking, but it is a concrete distributed-inference systems paper with real network-facing pipeline behavior, activation relay design, and latency sensitivity.

Key insights:

  • The network payload is activations, not KV pages; the critical path is per-token pipeline stage latency plus relay overhead.
  • Compiler/runtime details matter as much as placement: a sharded model can lose vendor optimizations unless the graph shape still triggers the right fusion.
  • Micro-batching multiple users across pipeline stages is the mechanism that hides bubbles, but it creates per-request cache ownership and scheduling concerns.
  • The wide-area-latency simulation makes a familiar point: pipeline parallelism can survive latency only when enough concurrent work fills the stages.

Actionable lessons: For heterogeneous or edge-fleet inference, benchmark the compiled shard, not just the monolithic model. Treat activation relay latency, stage imbalance, and cache ownership as first-class design variables, and validate that graph transformations preserve vendor fusions.

RetryGuard: Preventing Self-Inflicted and Attack-Driven Retry Storms in Cloud Applications

Authors & affiliations: Jhonatan Tavori, Anat Bremler-Barr, Hanoch Levy, and Ofek Lavi. Jhonatan Tavori — Columbia University; Anat Bremler-Barr, Hanoch Levy, and Ofek Lavi — Tel Aviv University.

Tags: Cloud Reliability, Transport/Retry Control, Microservices

Problem: Independent microservice autoscalers and default retry policies can create retry storms during overload or adversarial pressure, amplifying latency, resource use, and cost instead of improving success probability.

Key contributions from the authors:

  • Introduces RetryGuard, a distributed framework that controls retries per service using an analytical model of retries, throughput/rejections, delay, and cost.
  • Compares against exponential backoff, jitter, and retry budgets, reporting large reductions in storm size, latency, and resource usage in simulations.
  • Demonstrates the approach in a multi-layer Kubernetes deployment with Istio, reducing peak replicas and cumulative memory usage under storm conditions.

Why it matters: This is adjacent rather than AI-cluster-specific, but the feedback-loop lesson is relevant: retries are a transport/control-plane mechanism, and uncoordinated “helpful” retransmission can become a load amplifier.

Key insights:

  • Retry control should be state-aware: a retry that helps under transient blocking can hurt under prolonged overload where downstream load stays above capacity.
  • Backoff and jitter reduce synchronization, but they do not necessarily answer whether a retry is productive for the service graph.
  • Service-mesh deployment matters because retry policy often lives below application logic but above transport; that is where storms can be controlled without rewriting every service.
  • The paper’s DoW framing is useful for inference services too: overload policies should account for cloud resource amplification, not only request success rate.

Actionable lessons: For LLM serving frontends, storage tiers, or metadata services, audit retry loops as coupled controllers. Put retry budgets behind service-state signals, and test overload with autoscaling delay, adversarial bursts, and multi-hop dependency chains.

SbDN: Source-based TSN-Grade Deterministic Networking using Commodity Switches

Authors & affiliations: Mohammadparsa Karimi, Majid Nabi, Andrew Nelson, Kees Goossens, and Twan Basten. All authors — Electronic Systems group, Department of Electrical Engineering, Eindhoven University of Technology (TU/e), Eindhoven, The Netherlands.

Tags: Deterministic Ethernet, Source Scheduling, Commodity Switches

Problem: TSN-grade bounded latency usually requires TSN-capable switches and complex per-switch configuration, making deployment costly and hard to reconfigure at runtime.

Key contributions from the authors:

  • Proposes SbDN, a source-based deterministic networking architecture that moves scheduling intelligence to a centralized multi-agent controller and enforces decisions at endpoints.
  • Introduces Temporal Network Partitioning for FIFO commodity switches and Traffic Prioritization for switches with strict-priority queues.
  • Provides formal deadline guarantees for admitted time-critical flows and evaluates 40 benchmark configurations across two topologies with low-millisecond scheduling times.

Why it matters: This is not an AI datacenter paper, but the architectural move is interesting for cluster fabrics: push determinism to endpoints/sources when the switching substrate is intentionally simple.

Key insights:

  • Endpoint/source scheduling can emulate some deterministic-network behavior without every switch participating in TSN.
  • Runtime reconfiguration becomes easier when the controller changes source release patterns instead of programming many switch ports.
  • The trade-off is admission control: the controller must know enough about topology, flow deadlines, and traffic classes to avoid overpromising.
  • For AI fabrics, the analogy is useful for collective/control traffic isolation on commodity Ethernet, even if the real timing regime differs from automotive/industrial TSN.

Actionable lessons: If commodity-switch deployment is a constraint, evaluate source-paced deterministic windows before reaching for specialized switching. Keep admission control explicit, and separate time-critical control/collective phases from best-effort bulk traffic in the model.
