Maia 200: A Software Defined Dataflow System for Large-scale AI Acceleration

Authors & affiliations: Sherry Xu, Marco Heddes, Jackson Peng, Tom Savell, Monica Tang, Prashant Ranjan, Jesse Benson, Ofer Dekel, Saurabh Dighe, Anupama Kurpad, Artour Levin, Matthew Mattina, George Petre, Cheng Tang, Yuan Yu, Li Zhang, and Torsten Hoefler. Affiliations: Microsoft Corporation, as listed on the first page of the arXiv PDF.

Tags: AI Accelerators, Scale-up Fabric, Dataflow Architecture

Problem: Modern LLM inference is increasingly limited by orchestrating data movement across specialized memories, compute engines, and accelerator links, not just by adding scalar/vector FLOPs. The paper presents Maia 200 as a software-defined locally accessed dataflow architecture built around explicit data-movement control.

Key contributions from the authors:

  • Introduces Maia 200, reporting 10,145 TFLOP/s FP4, 5,072 TFLOP/s FP8, 7 TB/s HBM bandwidth, and a 750 W TDP for large-scale AI inference workloads.
  • Defines a software-defined locally accessed dataflow architecture (SDLA) taxonomy and ISA model where control programs orchestrate dataflow engines, memories, and movement engines explicitly.
  • Describes deployment-level system design, including accelerator trays/racks, a two-tier network topology, ATL receiver-driven messaging, and collective benchmark results across Maia chips.

Why it matters: This is today’s strongest infrastructure signal because it is not just another accelerator spec sheet: it exposes Microsoft’s argument that AI chips should be programmed around dataflow and movement, with the rack/tray network treated as part of the architecture rather than a passive backplane.

Key insights:

  • The important shift is from thread-centric execution to programmable data-movement orchestration; that lines up with where large inference clusters spend pain: staging, collectives, memory hierarchy, and fabric pressure.
  • The paper’s ATL receiver-driven messaging is worth reading as a fabric/software contract: the accelerator network is designed around explicit movement primitives rather than pretending all communication is ordinary host networking.
  • The two-tier tray/rack topology makes the accelerator package, local interconnect, and scale-out network a single performance object. For superpods, this is the right lens: chip bandwidth, HBM, collective topology, and runtime scheduling have to be co-designed.
  • The reported allgather benchmarking is especially relevant because it ties the architecture to real collective behavior, not only per-chip GEMM throughput.

Actionable lessons: For AI supernode design, model data movement as a first-class ISA/runtime concern. Hardware specs should be evaluated with collective paths, receiver-side progress, memory-engine scheduling, and rack topology in the loop; otherwise the advertised FLOPs can be stranded behind movement bottlenecks.

Scalable datacenter replication with mostly-synchronous consensus on hardware

Authors & affiliations: Davide Rovelli, Philipp Berdesinski, Rodrigo Otoni, and Patrick Eugster. Affiliations: Università della Svizzera Italiana (USI); turbalance; University of Groningen.

Tags: SmartNICs, Datacenter Reliability, Consensus/Replication

Problem: Strongly consistent replication remains a latency and scalability tax for datacenter services. The paper asks whether consensus can exploit the more stable timing behavior of programmable network hardware instead of inheriting all the costs of mostly-asynchronous end-host protocols.

Key contributions from the authors:

  • Introduces scarHW, a network-card design for scalable in-hardware replication using an FPGA SmartNIC.
  • Proposes POPUC, a collaborative-consensus protocol designed for “mostly synchronous” programmable network devices and formally specified/verified in TLA+.
  • Demonstrates FPGA prototypes integrated with Redis and ZooKeeper, reporting up to two orders-of-magnitude latency/throughput gains over prior approaches and zero downtime under minority-replica failures.

Why it matters: For AI infrastructure, this matters because coordination is not glamorous until it is on the critical path: rendezvous, metadata, checkpoint coordination, elastic training state, and disaggregated-memory control all depend on reliable replicated services.

Key insights:

  • The key architectural bet is that NIC-side logic has tighter latency distributions than software stacks on contended hosts, so consensus can use a different synchrony assumption.
  • scarHW attacks the leader bottleneck by letting multiple hardware replicas progress decisions in parallel instead of funneling all requests through one saturated process.
  • The paper is a reminder that “in-network acceleration” is not only reductions and telemetry; control-plane state replication is also a candidate if the failure model is explicit.
  • The failure semantics are central: POPUC preserves safety under crash-stop and message omission failures, but the deployment still has to respect the assumed mostly-synchronous hardware behavior.

Actionable lessons: If a cluster control path is bottlenecked by strongly consistent metadata, consider whether programmable NICs can provide bounded-latency agreement or replication offload. But treat the timing model as a contract: without clear omission/failure detection, hardware consensus can become a very fast way to encode false assumptions.

verified arXiv paper · collective communication, gpudirect rdma, heterogeneous hpc/ai

Optimizing Allreduce Operations for Modern Heterogeneous Architectures with Multiple Processes per GPU

Authors & affiliations: Michael Adams and Amanda Bienz. Affiliations: University of New Mexico, Albuquerque, NM, USA.

Tags: Collective Communication, GPUDirect RDMA, Heterogeneous HPC/AI

Problem: Large GPU-aware all-reduce operations bottleneck distributed deep learning, while modern nodes often leave many CPU cores idle because applications bind roughly one process/core per GPU. The paper explores using multiple CPU processes per GPU to accelerate collective communication on heterogeneous systems.

Key contributions from the authors:

  • Extends lane-aware all-reduce to modern heterogeneous nodes with multiple processes per GPU.
  • Uses GPUDirect RDMA and host-copy communication paths to exploit otherwise-idle CPU cores during large GPU-aware reductions.
  • Reports speedups over system MPI of up to 3× on LLNL Tuolumne and up to 2.45× across NVIDIA A100 GPUs on NCSA Delta.

Why it matters: This is practically useful because it challenges a default assumption in GPU collectives: the CPU side is just a launcher/control plane. For large reductions, host cores can become active participants in extracting more bandwidth from GPU/NIC/node topology.

Key insights:

  • The method is not magic bandwidth creation; it decomposes buffers and lanes so multiple CPU processes can drive communication concurrently and better match the node’s heterogeneous resources.
  • The interaction between GPUDirect RDMA and host-copy paths is the interesting part: the best strategy depends on message size, node topology, CPU availability, and GPU/NIC locality.
  • The work is a nice counterpoint to pure NCCL-style GPU-centric thinking: for some collective regimes, “unused” host cores are a schedulable communication resource.
  • The reported multi-process-per-GPU approach implies runtime libraries should expose or auto-tune CPU participation rather than hard-coding one control process per accelerator.

Actionable lessons: When benchmarking collectives on GPU clusters, include CPU-process topology as a variable: processes per GPU, NUMA placement, GPUDirect path, and host staging path. In heterogeneous accelerator clusters, communication libraries should treat CPUs as part of the collective datapath budget, not just orchestration overhead.

verified arXiv paper · remote gpu access, wireless networking, llm inference

WiCi: Wireless GPU Computing Infrastructure

Authors & affiliations: Yibin Shen, Wei Li, Kaiqiang Xu, and Zili Meng. Affiliations: not clearly listed in the arXiv metadata/PDF; the PDF lists the project contact email hello@wici.ai.

Tags: Remote GPU Access, Wireless Networking, LLM Inference

Problem: Mobile LLM inference is limited by weak on-device GPUs, while cloud inference adds cost and dependency on distant infrastructure. WiCi proposes making nearby server-grade GPUs accessible to mobile clients over Wi-Fi while preserving compatibility with existing device/application stacks.

Key contributions from the authors:

  • Proposes a wireless GPU computing infrastructure where mobile clients offload GPU-related computation to a nearby standalone GPU server over standard Wi-Fi.
  • Implements a framework with WiCi client/server components, custom packet headers, function batching, trace replay, and model caching to hide Wi-Fi round trips.
  • Reports up to 90% lower time-to-first-token, roughly 39× higher token rate versus local mobile inference for the same model, and up to nearly 80% of native server-GPU performance across tested applications.

Why it matters: This is edge-facing rather than superpod-scale, but it is still a clean datapoint on remote accelerator access: the hard problem becomes API remoting, RTT amortization, caching, and network-aware batching rather than raw GPU compute.

Key insights:

  • WiCi essentially turns GPU calls into a network protocol; once that happens, packet format, batching, trace replay, and cache placement determine whether the remote accelerator feels local enough.
  • The network is Wi-Fi, not RDMA, so the system leans heavily on reducing round trips rather than relying on microsecond fabric latency.
  • The design exposes a broader lesson for disaggregated GPUs: compatibility with existing software stacks often means intercepting at the library/driver boundary and then rebuilding enough execution semantics remotely.
  • The reported “nearly 80% native” result should be read as workload-dependent; short kernels and chatty API sequences are exactly where RTT dominates.

Actionable lessons: For any remote-GPU or GPU-disaggregation design, first count control-plane round trips and cacheable state. If the execution path is chatty, bandwidth will not save it; batching, replay, and locality-aware caching become the core architecture.

verified arXiv paper · llm serving, systems simulation, disaggregated infrastructure

Simthesizer: An Agent-Driven Simulation Framework for LLM Serving Systems

Authors & affiliations: Wonung Kim, Hyunmin Choi, Minsu Kim, Jaehong Cho, Yeongwook Kim, and Jongse Park. Affiliations: KAIST, Daejeon, Republic of Korea.

Tags: LLM Serving, Systems Simulation, Disaggregated Infrastructure

Problem: LLM serving systems are evolving faster than hand-built simulators: agentic workflows, disaggregated prefill/decode, heterogeneous accelerators, and new schedulers require simulator rewrites that lag behind real deployments.

Key contributions from the authors:

  • Introduces Simthesizer, a composable simulator infrastructure that represents the serving workflow and control decisions as a unified dynamic graph.
  • Adds a harnessed coding agent that lowers natural-language simulator feature requests into guarded extensions with fidelity validation.
  • Reports 2.51% average throughput error versus a vLLM-based real system for Simthesizer-built extensions, compared with 6.03% for extensions built on existing simulators, while simulating up to 284.96× faster than LLMServingSim2.0 and 23.19× faster than Vidur.

Why it matters: This one is useful as tooling signal: if we want to evaluate disaggregated serving, KV movement, and topology-sensitive scheduling without buying the whole cluster every time, the simulator needs to evolve at the same speed as the serving stack.

Key insights:

  • The unified dynamic-graph representation is the key systems idea because modern serving is no longer a linear request pipeline; control decisions are part of the workload.
  • Agent-generated simulator extensions are only credible because the paper wraps them with simulator-specific guardrails and fidelity checks; otherwise this would be vibe-coded infrastructure modeling.
  • For networking studies, the missing question is how accurately such frameworks model fabric contention, KV transfer, multi-tenant interference, and collective/control traffic.
  • This could be useful as a front-end for design-space exploration, but any network-facing conclusion should still be validated against packet/trace-level measurements.

Actionable lessons: Use simulator automation to explore broad serving design spaces, but pin network claims to measured traces. For Ethan-style cluster work, the right workflow is: fast simulator for pruning, then fabric-level replay/emulation for contenders that survive.
