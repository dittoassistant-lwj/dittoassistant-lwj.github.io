AI cluster networking & infrastructure brief

Today’s best signal is about fabric-aware execution rather than generic serving policy: staged LLM-serving traffic, device-initiated MoE communication, OCS logical topology, and multi-rail GPU path balancing. Most important paper of the day

Multi-stage Flow Scheduling for LLM Serving

Authors & affiliations: Yijun Sun, Xudong Liao, Songrun Xie, Wenxue Li, Yiming Zhang, Hao Chen, Han Tian, and Kai Chen. Affiliations: iSING Lab, Hong Kong University of Science and Technology; Shanghai Jiao Tong University; University of Science and Technology of China.

Tags: LLM Serving, Network Scheduling, KV / Collective Traffic

Why this is the top pick: This is the strongest signal for Ethan today because it treats the LLM serving data path as a dependency graph over network stages, not as independent byte transfers. That is exactly where disaggregated serving, KV reuse, collectives, and P2D handoff start to collide in real clusters.

Deeper explanation: MFS reframes disaggregated serving as a staged dependency problem over the network. In a prefill/decode system with KV reuse, a request may need remote KV-block retrieval before collective synchronization, then P2D transfer before decode can emit the first token. Those stages share bottleneck links, and contention can happen both within one request and across requests. The paper’s Reverse Multi-Level Queue mechanism is interesting because it approximates least-laxity-first behavior without assuming the scheduler knows exact remaining slack. Architecturally, the takeaway is that TTFT is controlled by the most poorly scheduled stage on the request’s network-critical path, not by average fabric bandwidth.

  • Problem: Modern disaggregated LLM serving turns TTFT into a multi-stage network problem: reusable KV-block retrieval, collective communication, and prefill-to-decode transfer can overlap and contend on shared links. Flow/coflow schedulers that ignore stage dependencies can spend bandwidth on the wrong phase and miss TTFT SLOs.
  • Key contributions: Introduces MFS, a holistic multi-stage flow scheduling mechanism for LLM serving that approximates Least-Laxity-First without needing exact remaining-slack estimates.; Uses a Defer-and-Promote principle with a Reverse Multi-Level Queue structure to prioritize flows as effective laxity shrinks while avoiding premature bandwidth consumption by loose-SLO requests.; Implements MFS as a pluggable vLLM module and evaluates it on an 8-server, 32-GPU testbed plus large-scale simulations, reporting 1.2×–2.4× higher TTFT SLO attainment over baselines.
  • Why it matters architecturally: Stage-aware scheduling is a natural bridge between LLM serving runtimes and transport/fabric policy. It exposes which bytes are urgent because they unblock first-token generation.
  • Useful diagram: Figure 1 contrasts multi-stage flow scheduling with stage-agnostic scheduling. Figure 2 lays out LLM serving at scale, while Figures 3 and 4 illustrate where KV-cache transfers, collectives, and P2D transfers contend on shared network paths.

Multi-stage Flow Scheduling for LLM Serving

Authors & affiliations: Yijun Sun, Xudong Liao, Songrun Xie, Wenxue Li, Yiming Zhang, Hao Chen, Han Tian, and Kai Chen. Affiliations: iSING Lab, Hong Kong University of Science and Technology; Shanghai Jiao Tong University; University of Science and Technology of China.

Tags: LLM Serving, Network Scheduling, KV / Collective Traffic

Problem: Modern disaggregated LLM serving turns TTFT into a multi-stage network problem: reusable KV-block retrieval, collective communication, and prefill-to-decode transfer can overlap and contend on shared links. Flow/coflow schedulers that ignore stage dependencies can spend bandwidth on the wrong phase and miss TTFT SLOs.

Key contributions from the authors:

  • Introduces MFS, a holistic multi-stage flow scheduling mechanism for LLM serving that approximates Least-Laxity-First without needing exact remaining-slack estimates.
  • Uses a Defer-and-Promote principle with a Reverse Multi-Level Queue structure to prioritize flows as effective laxity shrinks while avoiding premature bandwidth consumption by loose-SLO requests.
  • Implements MFS as a pluggable vLLM module and evaluates it on an 8-server, 32-GPU testbed plus large-scale simulations, reporting 1.2×–2.4× higher TTFT SLO attainment over baselines.

Why it matters: This is the strongest signal for Ethan today because it treats the LLM serving data path as a dependency graph over network stages, not as independent byte transfers. That is exactly where disaggregated serving, KV reuse, collectives, and P2D handoff start to collide in real clusters.

Key insights:

  • The paper’s key move is to schedule communication at request-stage granularity: KV retrieval, collectives, and P2D transfer have different downstream consequences for TTFT.
  • Coflow is not enough for this workload; a coflow groups related transfers, but it does not encode the stage order that determines whether a token can be emitted.
  • The “laxity” framing is useful because user-visible SLO miss risk depends on remaining end-to-end slack, not just current flow size or deadline.
  • For disaggregated serving, the network bottleneck can move between remote KV fetch, activation synchronization, and P2D transfer as request mix changes.
  • The vLLM integration makes this more than a simulator idea; it suggests a path to inserting network-aware scheduling into real inference stacks.

Actionable lessons: For serving architecture work, model TTFT as a staged network-critical path. Treat KV retrieval, collective synchronization, and P2D transfer as separately schedulable traffic classes with dependencies. If building a simulator, do not collapse all prefill communication into one bandwidth term; stage ordering changes which contention is harmful.

NCCL EP: Towards a Unified Expert Parallel Communication API for NCCL

Authors & affiliations: Amos Goldman, Nimrod Boker, Maayan Sheraizin, Nimrod Admoni, Artem Polyakov, Subhadeep Bhattacharya, Fan Yu, Kai Sun, Georgios Theodorakis, Hsin-Chun Yin, Peter-Jan Gootzen, Aamir Shafi, Assaf Ravid, Salvatore Di Girolamo, James Dinan, Xiaofan Li, Manjunath Gorentla Venkata, and Gil Bloch. Affiliations: NVIDIA Corporation.

Tags: NCCL, MoE Communication, GPU-Initiated RDMA

Problem: MoE expert parallelism uses fine-grained dispatch/combine all-to-all traffic that does not fit classic CPU-orchestrated collectives well. Existing device-initiated MoE communication libraries show the latency benefits of GPU-initiated RDMA, but fragment APIs and communication stacks outside NCCL.

Key contributions from the authors:

  • Presents NCCL EP, a MoE communication library built on NCCL’s Device API with unified ncclEpDispatch and ncclEpCombine primitives.
  • Provides low-latency mode for decode and high-throughput mode for training/prefill, using direct RDMA+NVLink mesh connectivity or hierarchical NVLink-domain aggregation before inter-node RDMA.
  • Evaluates H100 multi-node configurations and shows integration with vLLM as a supported path for expert-parallel communication on NVIDIA platforms.

Why it matters: MoE communication is becoming a first-class transport workload: tiny decode dispatches want latency, while prefill/training dispatches want bandwidth. NCCL EP is important because it brings device-initiated expert communication into the standard NCCL ecosystem rather than leaving it as a pile of bespoke kernels.

Key insights:

  • The paper cleanly separates low-latency decode from high-throughput prefill/training; one API surface can hide two very different transport strategies.
  • GPU-initiated RDMA matters because CPU orchestration overhead becomes visible for small, frequent MoE dispatch/combine operations.
  • Hierarchical aggregation inside NVLink domains before inter-node RDMA is the right instinct for reducing pressure on the scale-out fabric.
  • Standardizing expert communication inside NCCL could make MoE runtimes more portable across vLLM, Megatron-like stacks, and future NVIDIA platforms.

Actionable lessons: For MoE system design, evaluate dispatch/combine separately for decode and prefill/training regimes. In fabric modeling, distinguish NVLink-domain aggregation, inter-node RDMA, and GPU-initiated control overhead. Watch API standardization: if NCCL EP becomes common, the network-facing primitive for MoE may shift from generic all-to-all to explicit dispatch/combine.

Useful diagram: Figure 1 shows the NCCL EP architecture and how low-latency kernels and high-throughput kernels connect through NCCL Device API, RDMA, and NVLink-aware paths.

Leaf-centric Logical Topology Design for OCS-based GPU Clusters

Authors & affiliations: Xinchi Han, Weihao Jiang, Yingming Mao, Yike Liu, Zhuoran Liu, Yongxi Lv, Peirui Cao, Zhuotao Liu, Ximeng Liu, Xinbing Wang, Changbo Wu, Zihan Zhu, Wu Dongchao, Yang Jian, Zhang Zhanbang, Yuansen Chen, and Shizhen Zhao. Affiliations: Shanghai Jiao Tong University; Xi’an Jiao Tong University; Nanjing University; Tsinghua University; University of Science and Technology of China; Shanghai Innovation Institute; University of Electronic Science and Technology of China; Huawei.

Tags: Optical Circuit Switching, GPU Cluster Topology, AI Datacenter Fabrics

Problem: OCS-based GPU clusters can dynamically configure inter-pod circuits, but spine-to-spine circuit choices can create routing polarization: some leaf-to-spine links become hot while parallel paths are underused, reducing ML training throughput.

Key contributions from the authors:

  • Defines the routing polarization problem in three-tier leaf-spine-OCS GPU clusters.
  • Introduces a leaf-centric logical-topology paradigm that balances traffic from the same leaf across multiple spine switches.
  • Provides a sufficient condition for avoiding routing polarization and a polynomial-time topology design algorithm, with simulations reporting up to 19.27% throughput improvement and 99.16% lower topology-computation overhead than MIP methods.

Why it matters: This is a practical OCS topology paper: it focuses on the awkward middle layer where optical circuits look abundant at the pod level but still bottleneck leaf-to-spine links. That is a nasty edge case for AI fabrics because collective/coflow traffic amplifies small imbalances.

Key insights:

  • The paper’s “routing polarization” term is useful: inter-pod bandwidth may look sufficient in aggregate while specific leaf-to-spine paths are overloaded.
  • A leaf-centric view is more deployment-realistic than only optimizing pod-pair bandwidth because servers enter the optical core through leaf/spine bottlenecks.
  • The result reinforces that OCS logical topology should be evaluated against routed traffic distribution, not just circuit count.
  • Polynomial-time topology design matters operationally; MIP-quality answers are less useful if they cannot keep up with workload changes or planning loops.

Actionable lessons: For OCS cluster designs, include leaf-to-spine utilization in the objective, not only pod-pair demand satisfaction. When reviewing optical topology proposals, ask whether the solution balances source leaves across spines or accidentally polarizes traffic. Use coflow-sensitive throughput metrics because ML jobs wait for the slowest congested slice.

Beyond Traffic Matrix: DELTA -- A DAG-Aware OCS Logical Topology Optimization for AIDCs

Authors & affiliations: Niangen Ye, Jingya Liu, Guofu Zhu, Weiqiang Sun, and Weisheng Hu. Affiliations: State Key Laboratory of Photonics and Communications, Shanghai Jiao Tong University; Huawei.

Tags: Optical Circuit Switching, LLM Training DAGs, AI Datacenter Fabrics

Problem: OCS fabrics cannot practically reconfigure inside every LLM training iteration, so operators need a static or slowly changing logical topology. Traffic matrices hide the time-varying concurrency and task slack in the training DAG, causing overprovisioning or missed bottlenecks.

Key contributions from the authors:

  • Introduces DELTA, a DAG-aware logical topology optimization framework for AI datacenters using computation-communication DAGs rather than only traffic matrices.
  • Formulates topology optimization as a MILP with variable-length time intervals and uses temporal slack from non-critical tasks to save optical ports without increasing iteration makespan.
  • Adds pruning and heuristic hot-starting to scale to thousand-GPU workloads, reporting up to 17.5% lower communication time and at least 20% lower optical-port consumption versus traffic-matrix baselines.

Why it matters: DELTA is valuable because it pushes OCS planning closer to the actual training schedule. For LLM clusters, the difference between “total bytes between pods” and “bytes on the critical path right now” is the whole game.

Key insights:

  • The paper argues that OCS topology should be generated from the computation-communication DAG because bandwidth demand is bursty and phase-dependent.
  • Slack-aware optimization is a good cross-layer lever: not every communication edge deserves the same optical capacity if it is off the critical path.
  • The static-per-iteration assumption is realistic for current OCS deployments because circuit, transceiver, NIC, and routing update times can exceed iteration-scale timing.
  • Port savings are architecturally important: reclaimed optical ports can be reallocated to bottlenecked workloads instead of treated as idle capacity.

Actionable lessons: For scale-up/scale-out optical studies, derive topology demand from model-parallel execution traces, not just averaged traffic matrices. Track critical-path slack and port budget together. If simulating OCS for training, include the practical no-intra-iteration-reconfiguration constraint; otherwise the design may be physically attractive but operationally fake.

From Skew to Symmetry: Node-Interconnect Multi-Path Balancing with Execution-time Planning for Modern GPU Clusters

Authors & affiliations: Jinghan Yao, Kaushik Kandadi, Bharath Ramesh, Hari Subramoni, and Dhabaleswar K. Panda. Affiliations: Department of Computer Science and Engineering, The Ohio State University.

Tags: Multi-rail Networking, GPU Interconnects, MoE All-to-All

Problem: Modern GPU nodes expose multiple heterogeneous paths—NVLink/NVSwitch or xGMI inside the node and multi-rail InfiniBand/RoCE across nodes—but static fastest-path or hash-striping schemes can leave many links idle under skewed All-to-Allv and MoE traffic.

Key contributions from the authors:

  • Proposes NIMBLE, an endpoint-driven runtime that redistributes traffic across intra-node and inter-node paths using capacity-normalized minimum-congestion optimization.
  • Uses a fast multiplicative-weights scheme plus CUDA-aware GPU-kernel RDMA pipelining through intermediate GPUs and rail-matched NICs.
  • Reports up to 2.3× higher intra-node bandwidth, 3.8× higher inter-node throughput, up to 5.2× over NCCL/MPI on skewed All-to-Allv, and 1.35× on end-to-end LLM MoE blocks.

Why it matters: This paper is a good reminder that “aggregate bandwidth” is not the same as usable bandwidth. AI clusters increasingly have many rails and intra-node paths, but skewed MoE and irregular all-to-all traffic can still bottleneck on a tiny subset of links.

Key insights:

  • The endpoint can act as a traffic orchestrator when the network fabric or collective library is too static to react to execution-time skew.
  • Intermediate-GPU routing sounds expensive, but the paper’s claim is that unused NVLink/NIC capacity can outweigh the extra hop under skew.
  • The target workload is highly relevant: skewed All-to-Allv is exactly the pattern that MoE dispatch/combine can produce.
  • Capacity-normalized optimization is the right metric when paths have heterogeneous bandwidths; raw path count is misleading.

Actionable lessons: For multi-rail GPU cluster design, measure per-link utilization under skewed collectives, not only average all-reduce bandwidth. Consider endpoint-driven rerouting when fabric-level adaptive routing cannot see GPU/NIC path imbalance. In MoE benchmarks, include skewed expert distributions; balanced synthetic all-to-all can hide the problem NIMBLE targets.

Useful diagram: Figure 1 is the key architecture intuition: skewed workloads overload selected intra-node/inter-node links, while NIMBLE redirects transfers through less busy paths to reduce the maximum link latency.

Fast take

Read MFS first if you care about disaggregated inference networks, then NCCL EP for where MoE communication APIs are heading. The two OCS papers are complementary: one says traffic matrices are too blunt, the other shows how pod-level optical plans can still polarize lower-layer links.
