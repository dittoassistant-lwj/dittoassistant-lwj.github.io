Most important paper of the day

TraCT: Disaggregated LLM Serving with CXL Shared Memory KV Cache at Rack-Scale

Authors & affiliations: Dongha Yoon, Younghoon Min, Hoshik Kim, Sam H. Noh, and Jongryool Kim. Affiliations: Virginia Tech; SK Hynix America.

Tags: LLM Serving, CXL/RDMA, KV Cache Transfer

Why this is the top pick: This is the strongest signal because it directly challenges a default assumption in disaggregated serving: that cross-worker KV movement is fundamentally a network transport problem. TraCT asks whether rack-local CXL memory can become the data plane instead.

Deeper explanation: TraCT is the paper I would read first because it sits exactly at the junction of LLM serving, rack-scale memory fabrics, and transport design. The system argues that prefill/decode disaggregation should not automatically imply NIC-mediated KV movement. By using CXL shared memory as a publish/consume substrate, it tries to turn rack-local KV exchange into a memory operation rather than a network operation. That is a big architectural claim: it potentially removes NIC queueing and transport variance, but replaces them with CXL consistency, metadata, and allocation problems. For Ethan’s world, the interesting question is not “CXL good, RDMA bad”; it is where the boundary should sit between scale-up memory semantics and scale-out transport semantics in AI pods.

Existing systems usually put that movement on RDMA/NIXL-style network paths, so KV transfer becomes sensitive to NIC queues, host buffering, transport overhead, and fabric contention.

TraCT: Disaggregated LLM Serving with CXL Shared Memory KV Cache at Rack-Scale

Authors & affiliations: Dongha Yoon, Younghoon Min, Hoshik Kim, Sam H. Noh, and Jongryool Kim. Affiliations: Virginia Tech; SK Hynix America.

Tags: LLM Serving, CXL/RDMA, KV Cache Transfer

Problem: Prefill/decode-disaggregated LLM serving saves GPU resources, but KV tensors still have to move from prefill to decode workers. Existing systems usually put that movement on RDMA/NIXL-style network paths, so KV transfer becomes sensitive to NIC queues, host buffering, transport overhead, and fabric contention.

Key contributions from the authors:

  • Proposes TraCT, a rack-scale LLM serving design that uses CXL shared memory both as the KV-transfer substrate and as a rack-wide prefix-aware KV cache.
  • Lets GPUs publish and consume KV blocks through CXL load/store and DMA paths, aiming to remove the NIC hop from disaggregated prefill/decode pipelines.
  • Adds software mechanisms for non-coherent CXL memory, including two-tier inter-node synchronization, CXL-side metadata/data management, and integration with NVIDIA Dynamo; reports up to 9.8× lower average TTFT, 6.2× lower P99 latency, and 1.6× higher peak throughput versus RDMA/DRAM-cache baselines.

Why it matters: This is the strongest signal because it directly challenges a default assumption in disaggregated serving: that cross-worker KV movement is fundamentally a network transport problem. TraCT asks whether rack-local CXL memory can become the data plane instead.

Key insights:

  • KV cache hits are not free in distributed serving; even when the prefix exists, moving it through NIC/host/transport layers can dominate TTFT and inject tail variance.
  • CXL changes the boundary between “memory hierarchy” and “network fabric”: the serving runtime can treat rack-local shared memory as a publication/consumption substrate for KV blocks.
  • The hard part is not only bandwidth. Non-coherent CXL memory creates metadata visibility, synchronization, allocation, and reclamation problems that the software stack must solve explicitly.
  • Prefix caching and transfer should be co-designed; separating them leaves reuse policy blind to the actual data-movement path.

Actionable lessons: For disaggregated inference architectures, model KV transfer as a first-class data plane with explicit choices: RDMA over fabric, CXL shared memory, host DRAM, or GPU-local HBM. If CXL is available rack-locally, evaluate whether metadata synchronization and capacity management are cheaper than repeated NIC-mediated transfers. The design question becomes “which path should own KV bytes at which scope,” not just “how fast is RDMA.”

Figure 3 details the two-tier inter-node locking scheme, and Figure 4 shows the software stack layered into Dynamo, CXL transfer, cache management, and synchronization.

PTStore (Prefix Tensor Store): Distributed Prefix Caching and Replication for High Throughput Inference Serving

Authors & affiliations: Meghana Maghyastha, Robert Underwood, Randal Burns, and Bogdan Nicolae. Affiliations: Johns Hopkins University; Argonne National Laboratory.

Tags: LLM Serving, Distributed KV Cache, RDMA

Problem: Prefix caching works well inside a node or GPU, but large serving deployments miss reuse opportunities when popular prefixes sit on other nodes. Fetching or regenerating those prefixes creates latency, load imbalance, and poor aggregate memory utilization.

Key contributions from the authors:

  • Introduces PTStore, a distributed tensor store for reusable KV-cache prefixes inspired by CDN-style caching and replication.
  • Stores prefixes at fine tensor granularity with consolidated metadata, enabling one-shot prefix queries rather than walking a distributed trie.
  • Adds popularity-aware replication to improve locality for hot prefixes; reports 5–6× more efficient execution than baselines that cannot aggregate KV memory across nodes/GPUs.

Why it matters: PTStore is useful because it treats KV prefixes as distributed infrastructure objects, not private runtime leftovers inside a single inference engine.

Key insights:

  • The CDN analogy is technically apt: hot prefixes should move closer to demand, but replication must be bounded by scarce GPU/host memory.
  • Metadata design is on the critical path. A distributed prefix cache that requires multi-hop lookup can erase the benefit of reuse.
  • RDMA I/O overhead still appears in the evaluation, which makes locality and replication policy part of the network optimization problem.
  • The system points toward a serving layer where cache placement, request routing, and memory-tier pressure need to be jointly controlled.

Actionable lessons: If building cross-node prefix caching, expose prefix popularity and remote-fetch latency to the scheduler. Replicate hot KV tensors based on observed demand and network locality, but keep a hard budget for duplicate KV memory. Treat the metadata path as latency-critical, not as a background control-plane detail.

DITRON: Distributed Multi-level Tiling Compiler for Parallel Tensor Programs

Authors & affiliations: Size Zheng, Xuegui Zheng, Hanshi Sun, Qi Hou, Wenlei Bao, Shiyu Li, Haojie Duanmu, Jin Fang, Chenli Xue, Chenhui Huang, Yuanqiang Liu, Renze Chen, Ningxin Zheng, Dongyang Wang, Li-Wen Chang, Liqiang Lu, Yun Liang, Jidong Zhai, and Xin Liu. Affiliations: ByteDance Seed; Peking University; Tsinghua University; Zhejiang University; Shanghai Jiao Tong University.

Tags: Distributed Kernels, Collectives, Heterogeneous GPU Clusters

Problem: LLM kernels increasingly combine compute with communication patterns such as AllGather+GEMM, ReduceScatter, AllReduce, tensor parallelism, sequence parallelism, and expert dispatch. Fixed libraries like NCCL are fast but rigid, while existing compilers often lack a good abstraction for multi-level distributed memory hierarchies.

Key contributions from the authors:

  • Introduces DITRON, a Triton-like distributed tile-level compiler with Core, Device, and Task tiling levels.
  • Maps fine-grained tiles to high-speed local domains and coarse-grained tiles to lower-bandwidth links, abstracting inter-node and intra-node communication.
  • Evaluates across NVIDIA/AMD and large clusters; reports 6–30% isolated-kernel speedups, 5–30% end-to-end inference gains in vLLM, and production deployment with large GPU-hour savings.

Why it matters: This is relevant to cluster networking because it pushes communication planning into the compiler abstraction instead of leaving it solely to hand-written collectives.

Key insights:

  • The paper’s memory-hierarchy framing is exactly the systems issue: NVLink/NVSwitch, PCIe, Ethernet, DMA/RDMA engines, and tensor cores all need different tile granularities.
  • Distributed swizzling is a compiler-level way to align tile order with collective communication, reducing mismatch between computation schedule and data-movement schedule.
  • EP dispatch/combine appears as a first-class compiler target, which is important as MoE traffic becomes a fabric stressor.
  • Portability across NVIDIA and AMD matters because heterogeneous AI infrastructure cannot assume one collective stack forever.

Actionable lessons: When designing new AI-cluster communication primitives, consider whether the optimization belongs in a runtime library, a compiler schedule, or both. For MoE and TP/SP kernels, make tile order and communication phase explicit enough that the compiler can reason about topology and link hierarchy.

CXLRAMSim v1.0: System-Level Exploration of CXL Memory Expander Cards

Authors & affiliations: Karan Pathak, David Atienza, and Marina Zapater. Affiliations: Embedded Systems Lab, EPFL; REDS, School of Engineering and Management Vaud, HES-SO.

Tags: CXL, Simulation, Scale-up Memory

Problem: CXL is becoming a key scale-up substrate for LLM memory expansion and KV-cache placement, but many simulators model CXL devices in simplified or architecturally inaccurate ways that cannot run unmodified Linux stacks or capture realistic latency/bandwidth behavior.

Key contributions from the authors:

  • Builds a gem5-integrated full-system simulator that places CXL memory devices at the I/O bus, closer to their architectural position.
  • Supports unmodified Linux 6.14+ kernels, CXL-CLI workflows, CXL.io/CXL.mem behavior, and common programming modes such as zNUMA/interleaving.
  • Calibrates against real hardware and highlights effects such as cache pollution when accessing CXL memory.

Why it matters: This is a tooling paper, but it matters because CXL-based LLM designs are easy to overclaim without a faithful memory/interconnect model.

Key insights:

  • CXL memory is not just “slower DRAM”; PCIe/CXL hierarchy placement, root-complex modeling, interleaving, and OS exposure shape observed behavior.
  • For LLM serving, the simulator is directly relevant to KV-cache tiering and CXL memory-pool experiments.
  • Cache pollution and heterogeneous NUMA effects can dominate the performance story if benchmarks only report aggregate bandwidth.
  • Architecturally correct simulation is a prerequisite for deciding whether CXL should replace, complement, or sit behind RDMA in a rack-scale design.

Actionable lessons: Use full-system CXL simulation before committing to rack-scale CXL memory policies. Evaluate page placement, interleaving, cache pollution, and kernel/driver behavior together. For AI workloads, test KV-cache access patterns rather than only STREAM-like bandwidth microbenchmarks.

Useful diagram: Figure 1 contrasts prior CXL simulator placement with CXLRAMSim’s I/O-bus placement, which is the key architectural point. Figure 2 shows the modeled x86 BIOS support needed to expose CXL 2.0 devices.

Versatile yet Efficient Network Traffic Analysis: Offloading Network Foundation Model to SmartNIC

Authors & affiliations: Chungang Lin, Xuying Meng, Tianyu Zuo, Weiyao Zhang, Meng Shen, Ruijie Zhao, Guanming Che, Ruiqi Meng, Ziyue Huang, Haitong Luo, Zhiwei Xu, and Yujun Zhang. Affiliations: Institute of Computing Technology, Chinese Academy of Sciences; University of Chinese Academy of Sciences; University of Virginia; Beijing Institute of Technology; Southeast University; Northeastern University, China; Haihe Lab of ITAI.

Tags: SmartNICs, Network Telemetry, AI at the Edge

Problem: Network foundation models can reduce label dependency for encrypted traffic analysis, but conventional model pipelines are too heavy for low-latency edge execution. Operators need traffic intelligence close to the packet path without dragging every decision back to host CPU/GPU.

Key contributions from the authors:

  • Presents Nepco, a network traffic analysis system that offloads a hardware-friendly network foundation model onto NVIDIA BlueField-3 SmartNICs.
  • Uses localized byte-sequence modeling and pattern-aware convolution/gating to avoid expensive global encoders while preserving task versatility.
  • Reports competitive macro-F1 versus strong network foundation model baselines while reducing end-to-end latency by 328× to millisecond scale, and outperforming hardware-offloadable models trained with far more labels.

Why it matters: This is less AI-cluster-specific than the KV/CXL papers, but it is a concrete SmartNIC/DPU data-plane acceleration result with real BlueField-3 constraints.

Key insights:

  • The paper is a reminder that “AI in the network” only works when the model architecture is co-designed with NIC memory, compute engines, and packet-processing constraints.
  • Localized byte importance is the enabling observation: many classification signals live in small regions, so global traffic transformers may waste both latency and DPU resources.
  • The BlueField-3 prototype exposes the split between host-side flexibility and NIC-side bounded execution.
  • For cluster operators, similar ideas could apply to fabric telemetry, anomaly classification, and in-path filtering—if the model is small and deterministic enough for the data plane.

Actionable lessons: For SmartNIC-based ML, start from the packet/data-path budget and then design the model, not the other way around. Keep feature extraction simple, quantify latency breakdown on the NIC, and reserve host fallback for cases that exceed on-NIC confidence or resource limits.
