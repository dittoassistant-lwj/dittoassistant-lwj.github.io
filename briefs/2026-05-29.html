Most important paper of the day

CXL-ClusterSim: Modeling CXL-based Disaggregated Memory Cluster for Pooling and Sharing using gem5 and SST

Authors & affiliations: Kaustav Goswami, Maryam Babaie, Hoa Nguyen, Venkatesh Akella, and Jason Lowe-Power (University of California, Davis).

Tags: CXL/disaggregated memory, Heterogeneous AI infrastructure, Simulation

Why this is the top pick: This is the most infrastructure-relevant paper in today’s batch because it gives architects a concrete way to study memory disaggregation before hardware exists. For Ethan’s world, CXL is not “just memory”: it changes where GPU/NPU jobs place state, how much traffic leaves the node, and what the fabric must tolerate when memory becomes a pooled resource.

Deeper explanation: CXL-ClusterSim matters because memory disaggregation is becoming a rack/pod-level architecture question for AI systems, not a local server feature. The paper combines detailed gem5 full-system nodes with SST orchestration so architects can study how remote memory ranges, pooling, sharing, CXL latency, OS behavior, and multi-node scaling interact. That is exactly the sort of tool needed before making claims about CXL-backed memory pools for LLM serving or training: the bottleneck may be page placement, TLB behavior, simulator synchronization, remote memory contention, or the interconnect path — not only nominal CXL bandwidth.

  • Why it matters architecturally: It gives a concrete full-system evaluation path for CXL-based pooled/shared memory designs that may reshape accelerator-cluster memory hierarchies.

New arXiv CS submission · CXL disaggregated memory / cluster simulation / AI memory pressure

CXL-ClusterSim: Modeling CXL-based Disaggregated Memory Cluster for Pooling and Sharing using gem5 and SST

Authors & affiliations: Kaustav Goswami, Maryam Babaie, Hoa Nguyen, Venkatesh Akella, and Jason Lowe-Power (University of California, Davis)

Tags: CXL/disaggregated memory, Heterogeneous AI infrastructure, Simulation

Problem: AI training and inference can require hundreds of GB to TB-scale memory with bursty peak-to-average demand, but CXL-based memory pooling and sharing are hard to evaluate because most tools lack full-system fidelity across multiple nodes.

Key contributions from the authors:

  • Builds CXL-ClusterSim by coupling gem5 full-system nodes with SST so multi-node CXL memory-pooling and sharing designs can be simulated.
  • Models OS-visible behavior such as TLBs, huge pages, NUMA policy, remote memory ranges, and remote memory blade behavior rather than only abstract bandwidth/latency.
  • Validates the simulator with STREAM and NPB-style workloads, then studies how CXL latency, pooling, sharing, and scaling affect bandwidth, IPC, and host memory footprint.

Why it matters: This is the most infrastructure-relevant paper in today’s batch because it gives architects a concrete way to study memory disaggregation before hardware exists. For Ethan’s world, CXL is not “just memory”: it changes where GPU/NPU jobs place state, how much traffic leaves the node, and what the fabric must tolerate when memory becomes a pooled resource.

Key insights:

  • Disaggregated memory performance depends on OS policy and address mapping, not only CXL link bandwidth; full-system simulation catches effects that simple NUMA emulation can hide.
  • Pooling and sharing create different bottlenecks: pooling helps capacity allocation, while sharing can become a communication substrate with coherence/latency sensitivity.
  • The simulator splits detailed node timing from scalable inter-node orchestration, which is the right pattern for exploring future rack/pod-scale CXL fabrics.
  • For AI clusters, memory underutilization and stranded capacity are architectural signals that the accelerator fabric and memory fabric may need to be co-designed.

Actionable lessons: When evaluating CXL memory-pooling roadmaps, avoid pure latency-bandwidth spreadsheets. Model page placement, TLB behavior, NUMA policy, OS overhead, and remote-memory contention under real model-serving/training traces. Treat memory disaggregation as a fabric problem, not a DIMM procurement trick.

New arXiv CS submission · datacenter switch buffers / queueing delay / transport FCT

BShare: Packet Queueing Delay-Driven Buffer Sharing for Datacenter Switches

Authors & affiliations: Krishna Agarwal, Muhamad Rizka Maulana, Vamsi Addanki, and Habib Mostafaei (Eindhoven University of Technology, The Netherlands; Purdue University, USA)

Tags: Datacenter switching, Buffer management/AQM, Transport performance

Problem: Switch buffer per port per bandwidth keeps shrinking, while bursty datacenter traffic needs shared buffers that prevent one queue from monopolizing memory without adding hardware-unfriendly estimation logic.

Key contributions from the authors:

  • Proposes BShare, a buffer-sharing mechanism that uses packet queueing delay as the congestion signal and needs only one operator-configurable parameter.
  • Avoids per-queue drain-rate estimation, floating-point control, ML prediction, or push-out operations that are difficult to deploy in line-rate programmable switches.
  • Uses ns-3 simulations to show improved FCT slowdown over static buffer management and up to 45.07% better FCT than ABM when paired with modern transport protocols such as PowerTCP under burst-heavy workloads.

Why it matters: This is not AI-specific, but it is directly relevant to AI fabric design: collective bursts, incast-like storage/checkpoint traffic, and MoE all-to-all phases all punish shallow buffers and bad buffer sharing. Delay-driven buffer admission is a deployability-oriented knob worth watching.

Key insights:

  • Queueing delay is a more direct congestion signal than occupancy alone because it reflects service pressure, not just instantaneous buffer fill.
  • The paper’s hardware-friendly design goal matters: many clever buffer schemes assume operations that current switches cannot perform at line rate.
  • Transport and buffer policy interact; the paper explicitly evaluates with Cubic, DCTCP, and PowerTCP rather than treating buffer management as isolated.
  • For AI clusters, shared-buffer interference across priorities or output ports can look like mysterious tail latency unless the switch exposes queue delay and drop behavior.

Actionable lessons: For AI-cluster Ethernet evaluations, include burst-heavy collectives and checkpoint/storage mixes when comparing buffer policies. Track per-queue delay, not only occupancy/drop counters. If a proposal needs drain-rate estimation or prediction in the fast path, ask whether the ASIC can actually do it.

New arXiv CS submission · RDMA security / P4 / Tofino data plane

Securing High-Performance Data Transfers: Implementing AES Encryption in RDMA Systems

Authors & affiliations: Erik Bångsbo, Zakaria Hersi, Anna Benktson, Stefan Holmgren, and Romaric Duvignau (Chalmers University of Technology; University of Gothenburg; Saab AB; Chalmers student and Saab intern affiliations listed for the first two authors)

Tags: RDMA/RoCE, Programmable switches, In-network security

Problem: RDMA’s CPU-bypass data path is valuable for HPC, storage, and ML systems, but its limited built-in encryption/authentication support creates risk in multi-tenant or untrusted environments; host-side encryption can undermine the performance point of RDMA.

Key contributions from the authors:

  • Implements AES-128 encryption for RDMA traffic directly inside a programmable Intel Tofino switch using P4.
  • Integrates variable-payload AES handling with RDMA packet processing under strict switch pipeline and resource constraints.
  • Reports proof-of-concept throughput up to 1.9 Gbps for 128-byte packets with very low packet loss, demonstrating feasibility but not yet line-rate production performance.

Why it matters: The numbers are modest, but the architectural direction is interesting: put protection in the network data plane so RDMA endpoints can remain lightweight and device-agnostic. This sits right at the SmartNIC/DPU/switch boundary Ethan cares about.

Key insights:

  • Security for RDMA is not just a crypto problem; it is a placement problem across CPU, NIC, switch, and transport semantics.
  • Programmable switches can centralize protection for many sources, but pipeline depth, parser constraints, and payload variability become first-order design limits.
  • The prototype is evidence of feasibility, not performance sufficiency; 1.9 Gbps is far below modern cluster-link rates, so this is a research step rather than a deployable superpod datapath.
  • The same pattern could be relevant for other in-network transformations if the operation is simple enough and the packet format is controlled.

Actionable lessons: When considering in-network security or transformation for RDMA/RoCE, separate three questions: whether the switch can parse the transport safely, whether the operation fits pipeline resources, and whether throughput scales to production link rates. Benchmark tiny packets and variable payloads, not only bulk streams.

New arXiv CS submission · KV cache reuse / long-context serving / heterogeneous cache pools

Adaptive KV Cache Reuse for Fast Long-Context LLM Serving

Authors & affiliations: Fei Li, Song Liu, Yan Liu, Jinhua Cui, Shiqiang Nie, Jinyu Wang, and Weiguo Wu (Xi’an Jiaotong University; Huazhong University of Science and Technology)

Tags: LLM serving, KV-cache movement, Heterogeneous storage/memory

Problem: Long-context LLM serving spends heavy TTFT in prefill. KV reuse can reduce recomputation, but non-prefix reuse breaks cross-chunk attention relationships, and moving reusable KV from GPU-external cache pools can turn I/O into the new bottleneck.

Key contributions from the authors:

  • Introduces CacheTune, a frequency-guided KV-cache reuse system that selectively recomputes semantic-critical tokens while reusing the rest.
  • Combines sparse KV transfer, asynchronous multi-stream overlap, deferred positional-encoding recovery, and hardware-aware recomputation-ratio tuning.
  • Reports 3.72×–4.86× TTFT speedup and 3.93×–6.21× throughput improvement while keeping generation quality close to full recomputation; with SSD/HDD cache pools, it reports 2.34×–2.36× TTFT speedup.

Why it matters: This is network-adjacent rather than pure networking, but it is a clean example of the “KV cache is a data-movement object” trend. As soon as reusable KV leaves HBM, cache reuse becomes a compute–I/O–fabric co-design problem.

Key insights:

  • Strict-prefix caching is too narrow for RAG/agent workloads where reusable chunks are assembled dynamically.
  • Selective recomputation can be cheaper than moving all KV, especially when the external cache tier is SSD/HDD or remote memory.
  • The system explicitly tunes the recomputation/movement balance, which is the right mental model for disaggregated serving.
  • Sparse KV transfer and overlap only help if the runtime can keep storage/network movement off the critical path.

Actionable lessons: For disaggregated serving designs, budget KV-cache movement explicitly: bytes moved, tier latency, overlap window, and quality loss from partial reuse. Do not assume cache hits are free if the hit lives outside HBM.

Useful diagram: Figure 5 gives the CacheTune workflow; Figure 6 shows the KV-cache offloading and sparse reuse pipeline. Figure 1 is useful for understanding the non-prefix cross-attention restoration problem.

Fast take

The shared theme is data movement outside the “happy path”: remote memory over CXL, burst absorption inside switch buffers, RDMA protection in a programmable switch, and KV-cache reuse when the cache lives beyond HBM.
