Most important paper of the day

Nuska: Stage-Aware Communication Scheduling for Disaggregated LLM Serving

Authors & affiliations: Yijun Sun, Xudong Liao, Songrun Xie, Hao Chen, Han Tian, Wenxue Li, Yiming Zhang, Kai Chen — iSING Lab, Hong Kong University of Science and Technology; Shanghai Jiao Tong University; University of Science and Technology of China.

Tags: LLM Serving, Network Scheduling, KV/Collective Traffic

Why this is the top pick: This is the strongest paper today because it is directly about the fabric-facing control loop of disaggregated inference. It treats KV fetches, collectives, and P2D transfers as dependent stages sharing bottleneck links, which is exactly where naive “just separate prefill and decode” designs start leaking tail latency.

Deeper explanation: Nuska is the most relevant because it moves disaggregated serving from placement thinking into fabric-control thinking. The paper’s model says TTFT depends on an ordered chain of network actions: fetch reusable KV blocks, run prefill-side collectives, then move state to decode. If these stages are scheduled independently, the cluster can waste scarce link time on traffic that is not yet urgent while a downstream stage blocks the first token. That is a useful mental model for large AI serving fabrics: the network should schedule request-critical dependencies, not anonymous byte streams.

  • Problem: Disaggregated LLM serving creates multi-stage network traffic on the TTFT critical path: reusable KV-block retrieval, collective communication during prefill, and prefill-to-decode transfer. Stage-agnostic flow/coflow schedulers can let early or loose-deadline traffic consume shared links while later latency-critical stages stall.
  • Key contributions:
  • Defines the multi-stage flow scheduling problem for disaggregated LLM serving and frames TTFT SLO misses as a network-dependency problem, not just a GPU scheduling problem.
  • Proposes Nuska, a pluggable scheduler that approximates Least-Laxity-First using a Defer-and-Promote principle and Reverse Multi-Level Queue structure, avoiding the need for exact remaining-slack estimation.
  • Integrates the design into vLLM and evaluates it on an 8-server, 32-GPU testbed plus simulations, reporting 1.2×–2.4× improvement in TTFT SLO attainment over baselines.
  • Why it matters architecturally: For disaggregated LLM serving, expose communication stages to the scheduler: KV retrieval, intra-prefill collectives, and P2D transfer should carry dependency and deadline metadata. If the network scheduler only sees byte flows, it will optimize the wrong object. A good design point is a runtime-integrated priority layer that prevents loose-deadline work from consuming scarce fabric capacity before it is actually urgent.

Nuska: Stage-Aware Communication Scheduling for Disaggregated LLM Serving

Authors & affiliations: Yijun Sun, Xudong Liao, Songrun Xie, Hao Chen, Han Tian, Wenxue Li, Yiming Zhang, Kai Chen — iSING Lab, Hong Kong University of Science and Technology; Shanghai Jiao Tong University; University of Science and Technology of China.

Tags: LLM Serving, Network Scheduling, KV/Collective Traffic

Problem: Disaggregated LLM serving creates multi-stage network traffic on the TTFT critical path: reusable KV-block retrieval, collective communication during prefill, and prefill-to-decode transfer. Stage-agnostic flow/coflow schedulers can let early or loose-deadline traffic consume shared links while later latency-critical stages stall.

Key contributions from the authors:

  • Defines the multi-stage flow scheduling problem for disaggregated LLM serving and frames TTFT SLO misses as a network-dependency problem, not just a GPU scheduling problem.
  • Proposes Nuska, a pluggable scheduler that approximates Least-Laxity-First using a Defer-and-Promote principle and Reverse Multi-Level Queue structure, avoiding the need for exact remaining-slack estimation.
  • Integrates the design into vLLM and evaluates it on an 8-server, 32-GPU testbed plus simulations, reporting 1.2×–2.4× improvement in TTFT SLO attainment over baselines.

Why it matters: This is the strongest paper today because it is directly about the fabric-facing control loop of disaggregated inference. It treats KV fetches, collectives, and P2D transfers as dependent stages sharing bottleneck links, which is exactly where naive “just separate prefill and decode” designs start leaking tail latency.

Key insights:

  • The useful abstraction is multi-stage flow, not isolated flow or coflow. A request can miss TTFT because one stage burns link time too early while a downstream stage with tighter effective slack waits.
  • KV-cache movement and collective communication should not be optimized independently; the paper argues that combining stage-local optimizers can amplify contention when their objectives conflict.
  • Defer-and-Promote is attractive operationally because it uses dynamic priority promotion rather than requiring precise future knowledge of request slack.
  • The system highlights a real deployment tension: SLO-aware network scheduling must be close enough to the serving runtime to understand request-stage dependencies, but lightweight enough not to become a new critical-path service.

Actionable lessons: For disaggregated LLM serving, expose communication stages to the scheduler: KV retrieval, intra-prefill collectives, and P2D transfer should carry dependency and deadline metadata. If the network scheduler only sees byte flows, it will optimize the wrong object. A good design point is a runtime-integrated priority layer that prevents loose-deadline work from consuming scarce fabric capacity before it is actually urgent.

verified arXiv paper · Disaggregated Serving, Multimodal LLMs, GPU Resource Control

EAServe: Encode-Aware Disaggregated Serving for Multimodal Large Language Models

Authors & affiliations: Kunxiong Zhu, Zhihao Shu, Hangyu Zheng, Minghai Qin, Miao Yin, Gagan Agrawal, Wei Niu — University of Georgia; Western Digital; University of Texas at Arlington.

Tags: Disaggregated Serving, Multimodal LLMs, GPU Resource Control

Problem: Multimodal LLM serving adds an Encode stage before Prefill and Decode. Existing text-only PD systems ignore Encode, while EPD systems often run it as a passive front-end service, leaving encode GPUs underutilized and starving downstream prefill/decode workers.

Key contributions from the authors:

  • Reframes Encode as the control point of the encode-prefill-decode pipeline rather than a pass-through stage.
  • Introduces EAServe with load-adaptive micro-batching, rate-controlled partial offload to a co-resident prefill worker, and dynamic SM partitioning for predictable co-location.
  • Adds Hybrid Auto Selection to search GPU allocation, encode batch size, and offload ratio; reports up to 4.3× and 1.7× higher goodput than NVIDIA Dynamo and vLLM under the evaluated SLOs.

Why it matters: This matters for infrastructure design because the new bottleneck is not only “where do we put prefill/decode?” but “who regulates admission into the whole pipeline?” For MLLM services, the modality encoder can become both a gateway and a hidden source of GPU underutilization.

Key insights:

  • EPD disaggregation is structurally different from PD disaggregation: every request must pass through Encode, so that stage controls downstream pressure.
  • Small per-request encode work can leave a modern GPU mostly idle, yet waiting for larger batches inflates latency; the system therefore needs controlled batching rather than a fixed microbatch policy.
  • SM partitioning is used as a local isolation/packing mechanism, which is relevant to mixed-stage serving even when the inter-node network is not the dominant bottleneck.
  • The design implicitly turns admission control into a cross-stage resource-allocation problem: encode rate, prefill placement, and GPU sharing all interact.

Actionable lessons: When adding modalities to a disaggregated serving architecture, do not bolt Encode on as a stateless proxy. Treat it as the admission-control and load-shaping stage for the pipeline. Measure per-stage utilization and downstream starvation together; otherwise a locally “cheap” encoder can quietly determine global goodput.

verified arXiv paper · Collective Communication, GPU Platforms, Sparse Training

SpCCL: A Sparsity-Aware Collective Communication Library for GPU Platforms

Authors & affiliations: Lannie Dalton Hough, Emir Gencer, Hoffmann Muki, Abhinav Bhatele — Department of Computer Science, University of Maryland, College Park.

Tags: Collective Communication, GPU Platforms, Sparse Training

Problem: GPU collective libraries such as NCCL generally communicate dense payloads even when application data is sparse. Sending only nonzeros can reduce traffic, but compression/decompression overhead, fill-in during reductions, and changing sparsity regimes can wipe out the benefit.

Key contributions from the authors:

  • Implements sparsity-aware all-gather, reduce-scatter, and all-reduce collectives for GPU platforms.
  • Introduces Pici, a bitvector-based sparse representation designed for low metadata overhead and fast GPU compression/decompression.
  • Adapts collective behavior to observed sparsity during the operation; reports up to 5.25× all-gather, 2.5× reduce-scatter, and 2.66× all-reduce speedups over NCCL at 99% input sparsity, plus 26% end-to-end speedup in a representative DDP case.

Why it matters: This is a good collective-communication signal because it attacks bytes-on-the-wire rather than only topology or algorithm choice. It is not a universal replacement for dense collectives, but it is a useful design point for sparse gradients, pruning-heavy training, and possibly structured activation/optimizer traffic.

Key insights:

  • The hard part is not recognizing sparsity; it is finding the crossover where saved network bytes exceed GPU compression, decompression, and format-conversion costs.
  • Fill-in during reduce-scatter/all-reduce means sparsity can decay inside the collective, so the representation and algorithm need to adapt mid-flight.
  • Pici’s bitvector format is a reminder that sparse metadata can become the new payload if the format is chosen poorly.
  • For AI cluster stacks, collective libraries may need data-aware fast paths rather than one dense abstraction that all workloads squeeze through.

Actionable lessons: If you are evaluating compression or sparsity in collectives, measure the full path: compression kernels, metadata overhead, network time, decompression, and sparsity decay. A transport-visible byte reduction is only useful if GPU-side transformation does not move the bottleneck back onto SMs or memory bandwidth.

Useful diagram: The paper’s figures are mostly format and performance oriented rather than a cluster architecture diagram. Figure 1 is useful for the Pici tile/bitvector representation, while the later performance figures show where sparse collectives beat dense NCCL baselines.

verified arXiv paper · Datacenter Networks, NetOps Agents, Routing Analysis

RoutingBench: Can Agentic Routing Analysis Scale to Production Datacenter Networks?

Authors & affiliations: Wenlong Ding, Zhixiong Niu, Jianan Yang, Fajun Zhang, Bo Zhang, Ling Liang, Yongqiang Xiong, Tianyin Xu, Hong Xu — The Chinese University of Hong Kong; Microsoft Research Asia; Microsoft; University of Illinois Urbana-Champaign.

Tags: Datacenter Networks, NetOps Agents, Routing Analysis

Problem: Agentic NetOps looks promising, but production routing-path analysis requires global reasoning over huge topologies, device configurations, BGP/static-route interactions, and change impact. Traditional symbolic tools can become slow or memory-bound at hyperscale.

Key contributions from the authors:

  • Introduces RoutingBench, a benchmark for agentic routing-path analysis across network sizes, topology complexity, and device-change types.
  • Compares in-context learning, iterative reasoning, and agent-skill approaches for path analysis under scale and context pressure.
  • Reports that curated agent skills following an “explore more; digest less” principle can analyze hyperscale networks of 50K routers with 99.5% accuracy in their setup, while also exposing failure boundaries on complex inter-DC scenarios and compound changes.

Why it matters: This is not an AI training-fabric paper, but it is relevant to Ethan’s world because hyperscale AI clusters still die by routing changes, gray failures, and operational blind spots. The interesting part is the scale boundary: whether agents can reason over network evidence without trying to stuff the whole fabric into context.

Key insights:

  • The benchmark focuses on routing-path analysis as a primitive: given a local config/device change, determine changed end-to-end paths and decisive evidence.
  • The “explore more; digest less” principle is a useful systems idea: let tools traverse large network state, but feed the model only compact decisive evidence.
  • The paper separates model protocol knowledge from scalable evidence discovery; the latter is the real blocker for production NetOps agents.
  • Agentic analysis may complement, not replace, symbolic analysis: symbolic tools struggle with scale, while agents still face accuracy boundaries on compound, inter-DC changes.

Actionable lessons: For AI-cluster operations tooling, do not ask an LLM to reason over raw configs at fabric scale. Build deterministic collectors and path explorers that return minimal, auditable evidence, then let the model reason over that evidence. The interface between tool and model matters more than prompt length.
