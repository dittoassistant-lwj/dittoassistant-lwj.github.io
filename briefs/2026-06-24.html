AI cluster networking & infrastructure brief

Today’s useful signal is infrastructure disaggregation: CXL plus RDMA memory pooling, KV-cache versus weight pool separation for cold MoE serving, and GPU-native data movement that avoids falling back through host memory.

Most important paper of the day

Aquifer: Hierarchical Memory Pooling with CXL and RDMA for MicroVM Snapshots

Authors & affiliations: Junliang Hu, Huaicheng Li, and Ming-Chang Yang. Affiliations: The Chinese University of Hong Kong, Department of Computer Science and Engineering; Virginia Tech, Department of Computer Science.

Tags: CXL/RDMA, Memory Disaggregation, Cloud Infrastructure

Why this is the top pick: Aquifer is the most directly architectural paper in the batch: it treats CXL and RDMA as a two-tier memory fabric with different latency, reach, and coherence properties. That is exactly the kind of trade-off that keeps showing up in AI superpod design, where not all “remote memory” should be treated as one uniform pool.

Deeper explanation: The paper’s key design choice is placement by access temperature. Hot MicroVM snapshot pages are served from a pod-local CXL pool; cold pages sit behind a cluster-wide RDMA pool. The hidden boss fight is correctness: CXL 2.0 multi-headed devices do not give full cross-host hardware cache coherence, so Aquifer has to add ownership-based coherence rather than assuming the fabric is magically shared memory.

  • Problem: Serverless MicroVM restore wants low-latency snapshot access and fleet-wide memory pooling, but CXL alone lacks reach and RDMA alone is too slow/expensive on the hot path.
  • Key contributions: Hotness-aware snapshot format, hierarchical CXL+RDMA placement, ownership-based coherence for CXL 2.0 MHDs, and copy-based page serving integrated with Firecracker.
  • Why it matters architecturally: It is a concrete example of tiered disaggregation: use the fast local fabric for the hot working set and the wider network fabric for capacity.
  • Useful diagram: Figure 1 shows the architecture: pod-level CXL memory under nodes, plus a cluster-level RDMA pool behind the network.
Fresh arXiv CS paper · CXL/RDMA memory pooling / serverless infrastructure / disaggregation

Aquifer: Hierarchical Memory Pooling with CXL and RDMA for MicroVM Snapshots

Authors & affiliations: Junliang Hu, Huaicheng Li, and Ming-Chang Yang. Affiliations: The Chinese University of Hong Kong, Department of Computer Science and Engineering; Virginia Tech, Department of Computer Science.

Tags: CXL/RDMA, Memory Disaggregation, Cloud Infrastructure

Problem: Memory stranding wastes substantial DRAM in cloud clusters, but flat remote-memory designs force an ugly trade-off: CXL gives low-latency load/store access only inside a small pod, while RDMA gives cluster-wide reach with higher latency and software overhead. Aquifer asks how to combine both tiers for latency-sensitive MicroVM snapshot restore.

Key contributions from the authors:

  • Characterizes MicroVM snapshot images across nine serverless workloads and finds that most pages are either zero or cold; the paper reports 82.8% zero pages and a small hot working set.
  • Designs a hierarchical CXL+RDMA snapshot-serving system for Firecracker-style MicroVMs: hot pages live in pod-local CXL memory, cold pages live in a cluster-level RDMA pool.
  • Adds an ownership-based coherence protocol for CXL 2.0 multi-headed devices without cross-host hardware cache coherence, plus copy-based page serving that pre-installs hot pages before resume and demand-pages cold pages asynchronously.

Why it matters: This is the cleanest infrastructure signal today because it treats CXL and RDMA as complementary tiers rather than competing memory-pooling answers. For AI infrastructure, the same design tension appears in KV pools, checkpoint/snapshot restore, cold model activation, and disaggregated memory services: fast pod-local capacity is useful, but the fleet wants a second, wider fabric tier.

Key insights:

  • The practical hierarchy is pod-local low-latency CXL plus cluster-wide RDMA over the existing network, not one giant coherent memory domain.
  • Snapshot hotness gives the placement policy a real signal: put the small latency-critical working set in CXL and use RDMA for capacity-heavy cold state.
  • CXL 2.0 multi-host sharing needs explicit correctness machinery because the hardware does not provide the coherence semantics many software designs implicitly assume.
  • The copy-based install path is a reminder that mmap-style tricks can break down when hot pages are sparse and shared images must remain immutable.

Actionable lessons: For disaggregated AI services, design the memory hierarchy around access temperature and coherence scope. Keep hot, latency-critical data near the accelerator/host; use RDMA for reach and capacity; and make coherence/ownership explicit instead of assuming future CXL hardware will magically erase placement costs.

Fresh arXiv CS paper · MoE serving / KV-cache pooling / GPU memory disaggregation

CrossPool: Efficient Multi-LLM Serving for Cold MoE Models through KV-Cache and Weight Disaggregation

Authors & affiliations: Zhuoren Ye, Tianyu Wo, Dinghao Xue, Mingming Zhang, Yuchen Teng, Chunming Hu, and Renyu Yang. Affiliations: School of Software, Beihang University.

Tags: LLM Serving, KV Cache, GPU Memory Pooling

Problem: Cold MoE models waste GPU memory because stable FFN weights and transient KV-cache compete inside the same HBM pool. Under low-concurrency traffic, KV-head-limited models such as MQA/GQA expose only a fraction of replicated KV capacity to a single request, weakening long-context support.

Key contributions from the authors:

  • Separates GPU memory into a weights pool for consolidated FFN weights and a KV-cache pool for active request state, keeping attention local to KV-cache and sending hidden states across the pool boundary.
  • Introduces a KV-cache planner/virtualizer, a layer-wise pipeline scheduler to overlap attention and FFN across batches, and GPU-resident persistent kernels/control lowering to reduce CPU-GPU scheduling overhead.
  • Evaluates against Static Partition and kvcached-style baselines and reports substantially better long-context cold-model serving, including up to 10.4x lower P99 time-between-tokens in the abstract.

Why it matters: CrossPool is not “just another scheduler”; it is a memory/fabric boundary proposal for serving many cold MoE models. The important move is choosing what crosses the boundary: hidden states, not accumulated KV-cache tensors. That is exactly the kind of data-plane decision that determines whether disaggregated serving stays bandwidth-sane.

Key insights:

  • Weights and KV-cache have different lifetimes; pooling them together hides capacity behind static model residency.
  • KV-cache visibility depends on attention parallelism. For cold traffic, DP replicas do not help a request if the request cannot see their KV memory.
  • The pool split works because FFN dominates MoE parameters, while attention needs local KV access whose footprint grows with context length.
  • Layer-wise pipelining is needed because hidden-state transfers occur every layer and every token; the design must overlap them instead of pretending they are free.

Actionable lessons: When designing multi-model serving, separate stable and transient state in the resource model. If a boundary is unavoidable, move bounded tensors across it and keep context-growing data local. Also measure “visible KV capacity per active request,” not just aggregate free HBM.

Useful diagram: Figure 3 is the system architecture: CPU ingress/control feeds a KV-cache HBM pool and an FFN-weights HBM pool connected by a low-latency data plane. Figure 2 is also useful because it visualizes why monolithic pooling wastes KV capacity for MQA/GQA under single-request cold traffic.

Fresh arXiv CS paper · disaggregated RL / heterogeneous GPU clusters / pipeline scheduling

Accelerating Disaggregated RL for Visual Generative LLMs with Diffusion-Based Parallelism and Trainer-Assisted Generation

Authors & affiliations: Sijie Wang, Zhengyu Qing, Zhiqiang Tan, Qiang Wang, and Shaohuai Shi: Harbin Institute of Technology, Shenzhen; Yiming Yin and Xiaowen Chu: The Hong Kong University of Science and Technology (Guangzhou); Yeqing Zhang and Yaoyuan Wang: Huawei Technologies Ltd.

Tags: Distributed Training, Heterogeneous GPUs, Pipeline Scheduling

Problem: Diffusion-oriented RL post-training for visual generative LLMs has different execution structure from autoregressive LLM RL. Colocating rollout generation and training simplifies synchronization, but couples resources, limits heterogeneous deployment, and leaves pipeline bubbles when generator/trainer times diverge.

Key contributions from the authors:

  • Introduces DigenRL, a disaggregated RL framework for diffusion-based generative LLMs that separates generator and trainer GPU groups and supports heterogeneous GPU allocation.
  • Adds generation-axis pipeline execution, time-step parallelism for trainer work, trainer-assisted generation that lets idle trainer GPUs help rollout, and trajectory-consistent stale synchronization bounded to one policy step.
  • Evaluates on 16-32 GPU testbeds with HunyuanVideo-13B, Wan2.1-14B, FLUX.1-12B, and QwenImage-20B, reporting 1.56-2.10x throughput over veRL-Omni and GenRL.

Why it matters: This is adjacent rather than pure networking, but it is relevant because RL post-training is becoming an AI-cluster workload with bursty inter-stage data movement and heterogeneous resource pools. The system lesson is about exposing the right parallelism axis so disaggregation does not simply move bubbles from one stage to another.

Key insights:

  • Diffusion RL has a small-batch, multi-timestep structure, so splitting only along the batch dimension produces too few pipeline units.
  • Time-step parallelism can amortize parameter all-gathers in FSDP/ZeRO-style training because one gathered parameter view does more work.
  • Heterogeneous GPU clusters make static generator/trainer partitioning fragile; idle trainer capacity can be temporarily recycled into generation.
  • The one-step stale policy constraint is a useful systems/algorithm compromise: more pipeline utilization without unbounded off-policy drift.

Actionable lessons: For post-training systems, profile generator/trainer bubbles separately and expose workload-specific parallelism rather than blindly reusing AR-LLM pipeline assumptions. On heterogeneous clusters, make resource roles elastic but bound staleness so the optimizer semantics remain defensible.

Fresh arXiv CS paper · GPU data systems / UCX / distributed GPU exchange

Accelerating Presto with GPUs

Authors & affiliations: Daniel Bauer, Luis Garces-Erice, Deepak Majeti, Zoltan Arnold Nagy, and Sean Rooney: IBM Research Europe / IBM Data & AI; Greg Kimball, Devavret Makkar, Todd Mostak, and Karthikeyan Natarajan: NVIDIA.

Tags: GPU Data Systems, RDMA/UCX, Distributed Execution

Problem: GPU-accelerated SQL engines lose much of their benefit if data repeatedly stages through CPU memory. Distributed queries make this worse: inter-worker exchange has to preserve GPU residency across machines, not just accelerate a single operator.

Key contributions from the authors:

  • Extends Presto/Velox with GPU-aware operators built around cuDF and Arrow-compatible data representations, with enough operator coverage to run TPC-H and TPC-DS queries on GPUs.
  • Implements GPU-native inter-worker exchange using UCX, selecting NVLink for same-machine transfers, RDMA for cross-machine transfers, and TCP fallback when needed.
  • Reports up to 20x faster exchange-heavy query behavior versus the standard Presto exchange path when data fits in cluster GPU memory, and up to 6x cost/performance improvement over CPU-only Presto on standard analytical benchmarks.

Why it matters: This is database infrastructure, but the fabric lesson maps well to AI clusters: once data is in accelerator memory, the distributed runtime should avoid falling back to host staging. UCX/RDMA/NVLink-aware exchange is the same broad pattern needed for GPU-native storage, feature pipelines, and inference/training data planes.

Key insights:

  • The authors validate three performance hypotheses: minimize CPU-GPU movement, retain working sets in GPU memory, and make inter-node exchange GPU-native.
  • Exchange-heavy distributed queries are a stress test for the data plane because every fallback to CPU memory inserts avoidable PCIe and serialization overhead.
  • UCX is used as a topology-aware transport layer, choosing NVLink, RDMA, or TCP according to endpoint capabilities.
  • The paper exposes a scheduler gap: GPU memory capacity, chunk size, skewed joins, and many small vectors become planning concerns, not just operator implementation details.

Actionable lessons: For accelerator-native data paths, make the exchange protocol a first-class design object. Track whether tensors/tables ever leave device memory, compact small messages before they poison GPU libraries, and make schedulers aware of cluster GPU memory rather than only CPU-side task placement.

Useful diagram: Figure 1 shows the motivating multi-GPU software architecture using GPFS, GPU-resident data, NVSHMEM, and UCX. Figure 2 shows how CPU Velox operators are translated into GPU-aware operators and where data sits in CPU versus GPU memory.

Fast take

Read Aquifer first for the memory-fabric design pattern: CXL for hot pod-local state, RDMA for cluster reach, explicit coherence where hardware stops helping. CrossPool is the serving-systems companion piece because it applies a similar separation instinct inside GPU HBM.
