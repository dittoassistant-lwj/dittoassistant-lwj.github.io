Conduit: An Experience Data Plane for Distributed Reinforcement Learning

Authors & affiliations: Sitong Zhang, Tuo Shi, Mario Di Francesco, Zeke Wang, and Bo Zhao — Aalto University; Shenzhen University of Advanced Technology; Zhejiang University.

Tags: Distributed RL, Experience Data Plane, Heterogeneous GPU Clusters

Problem: Distributed RL systems increasingly treat the experience buffer as a latency-critical data path, not just a replay queue. Actor rollout, CPU/GPU memory placement, node-to-node movement, sampling, batching, and learner delivery all sit on the iteration critical path, but existing frameworks tend to hide those controls inside framework logic or fixed buffer services.

Key contributions from the authors:

  • Defines an Experience Data Plane (EDP) abstraction that separates RL experience-ingestion, placement, and delivery semantics from framework-specific execution logic.
  • Introduces capacity-constrained, bandwidth-aware placement across CPU/GPU memory tiers and nodes under heterogeneous interconnect and device-memory constraints.
  • Adds latency-aware scheduling for experience-path work; integrated with RLlib, Conduit reports up to 97% lower exposed experience-path latency, up to 38% lower end-to-end iteration latency, and scaling to 1,024 GPUs while preserving convergence.

Why it matters: This is the strongest systems/networking signal today. It is not a classic transport paper, but it makes the data plane of distributed RL explicit: placement and movement of experience become schedulable infrastructure primitives across heterogeneous GPU clusters.

Key insights:

  • The paper reframes the experience buffer as a distributed storage and data-movement substrate, which is the right mental model once RL post-training scales past a single-node queue.
  • The useful abstraction is not “better replay buffer”; it is “separate data-plane semantics from framework control flow” so placement and scheduling can evolve independently.
  • Bandwidth-aware placement matters because experience state spans CPU memory, GPU memory, and inter-node links; a capacity-only policy can still expose latency if the next learner step waits on the wrong tier or path.
  • The RLlib integration is valuable because it suggests the approach can wrap existing frameworks without rewriting algorithm logic.

Actionable lessons: For large-scale RL/post-training infrastructure, expose experience movement as a first-class data path with observability and placement controls. Treat rollout-to-learner delivery like a fabric workload: model memory tiers, link bandwidth, batching points, and whether preprocessing work is hidden or exposed on the critical path.

SPECTRA: Adaptive Execution of Speculative Decoding on a Runtime-Reconfigurable Tiled Architecture

Authors & affiliations: Gabriele Tombesi, William Baisi, Je Yang, Elisavet Lydia Alvanaki, Kevin Lee, Michael Lippe, Biruk Seyoum, and Luca P. Carloni — Columbia University.

Tags: LLM Inference, Reconfigurable Architecture, Communication Patterns

Problem: Speculative decoding shifts LLM inference between memory-bound GEMV-like decode, compute-bound GEMM-like prefill, and an intermediate verification regime whose arithmetic intensity changes with speculation length and acceptance rate. Fixed accelerator datapaths and static tile partitioning leave utilization on the floor.

Key contributions from the authors:

  • Proposes SPECTRA, a runtime-reconfigurable tiled architecture for speculative decoding that adapts both tile-level compute mode and system-level parallelism per kernel.
  • Switches each tile between systolic GEMM execution and vector-lane GEMV execution while dynamically selecting tile count, partitioning, and communication patterns across tiles.
  • Evaluates a 20-tile FPGA prototype on Pythia, SmolLM2, and GPT-2 workloads, reporting up to 2.09× speedup from tile-level reconfiguration and an additional 1.25× from system-level adaptability.

Why it matters: For Ethan’s infrastructure lens, this is interesting because it treats speculative decoding as a runtime-changing communication/computation mapping problem. Even at edge scale, the same lesson applies to accelerator pods: static parallelization is brittle when token acceptance and phase mix move at runtime.

Key insights:

  • Verification in speculative decoding is neither ordinary decode nor ordinary prefill; it creates a middle regime where both compute shape and data movement pattern need to adapt.
  • The paper’s two-level adaptation is the key: local PE-array mode changes are not enough unless the architecture also changes how work and communication are distributed across tiles.
  • Acceptance rate becomes a systems parameter, not only an algorithm metric, because it changes how much parallel verification work is useful.
  • The design points toward accelerator fabrics where kernels carry enough metadata for runtime partitioning rather than relying on a fixed collective/dataflow plan.

Actionable lessons: When designing inference accelerators or serving kernels, classify phases by arithmetic intensity and communication pattern rather than by model layer name alone. Runtime systems should be able to remap tile/device parallelism when acceptance rate, batch shape, or context phase changes.

Tiga: Compiling Graph Message Passing at Scale

Authors & affiliations: Mingyuan Chi — Independent Researcher.

Tags: Distributed Graph Processing, Compiler Runtime, Out-of-Core GPU Execution

Problem: Graph/message-passing workloads often lose their interaction structure when lowered into tensor operations, causing unnecessary materialization of edges/messages, device-memory pressure, and hard-to-control communication/load-balance behavior across devices.

Key contributions from the authors:

  • Builds a JIT compiler that keeps graph relations, reducer algebra, and field roles visible in a multi-level IR so traversal, storage, and lowering can be specialized.
  • Supports fusion of relation generation with aggregation, reverse-mode autodiff, CPU/GPU lowering, and out-of-core execution via graph partition streaming through host memory with page-sized GPU staging buffers.
  • Extends the programming model to distributed execution through partition ownership and halo exchange, with measurements characterizing communication and load-balance costs.

Why it matters: This is adjacent rather than pure AI-cluster networking, but the mechanism is relevant: preserving relation structure lets the runtime choose where communication and storage happen instead of blindly materializing giant intermediate tensors.

Key insights:

  • The compiler-visible relation is the main systems trick; it lets generated neighbors be consumed directly instead of forcing a full edge/message materialization step.
  • The storage hierarchy is explicit: device memory becomes an active staging tier, not the capacity limit for the graph.
  • Distributed execution is framed as ownership plus halo exchange, making communication cost part of the lowering decision.
  • The result is a useful reminder that AI/data-processing runtimes need logical communication structure preserved late enough for placement and transfer decisions.

Actionable lessons: For graph-like AI workloads, avoid lowering too early into generic dense tensor steps. Keep relations, reducers, ownership, and halo traffic visible so the runtime can fuse work, page data, and choose communication patterns based on memory pressure and topology.

Dissecting How Die Scaling Breaks GPU Fine-grained Scheduling

Authors & affiliations: Xiaoze Fan, Jianhao Wang, Weihao Cui, Han Zhao, Zhuobin Huang, Yangjie Zhou, Yuxian Qiu, Shixuan Sun, Bingsheng He, Quan Chen, and Minyi Guo — Shanghai Jiao Tong University; National University of Singapore; NVIDIA.

Tags: GPU Architecture, Topology-Aware Scheduling, Heterogeneous AI Infrastructure

Problem: Modern large GPUs are not physically uniform: floorswept SMs, cache/memory partitioning, and non-uniform memory paths make logical “same-sized” GPU allocations perform differently. Existing fine-grained schedulers usually allocate counts of resources rather than specific physical resources.

Key contributions from the authors:

  • Develops lightweight characterization methods to uncover per-chip compute topology and memory affinity hidden behind GPU logical abstractions.
  • Shows that topology-oblivious allocation can cause up to 1.33× performance variation, while remote HBM access raises latency by up to 67% and nearly doubles L2 latency.
  • Uses discovered topology and affinity to make fine-grained scheduling asymmetry-aware, improving mainstream kernels by up to 1.22× and multiplexed LLM inference by up to 14.3%.

Why it matters: This is squarely relevant to heterogeneous AI infrastructure. The “cluster topology” story is no longer only rack/fabric-level; within a GPU, physical resource placement can leak into scheduling, co-location, and tail performance.

Key insights:

  • Logical GPU resource abstractions hide meaningful physical placement differences, especially as die scaling and floorsweeping become normal.
  • Fine-grained scheduling needs both quantity and identity: which SMs/GPCs/L2 partitions are assigned can matter as much as how many.
  • Multiplexed LLM inference is sensitive to these effects because co-located kernels and memory paths amplify small asymmetries into latency/throughput variation.
  • This is a warning for cluster schedulers too: per-GPU telemetry may need sub-device topology annotations if MIG-like partitioning and multiplexing are used aggressively.

Actionable lessons: When evaluating GPU partitioning or co-location policies, measure per-chip topology and memory affinity instead of assuming homogeneous slices. Feed that characterization into placement/scheduling, especially for latency-sensitive inference and mixed-kernel serving.
