Daily brief · 2026-05-28

AI cluster networking & infrastructure brief

Today’s useful signal is split between the network interface boundary and MoE serving data movement: one paper tries to break RDMA’s Queue-Pair-over-PCIe shape, while the others map where disaggregation, checkpoint I/O, and AlltoAll imbalance actually bite in modern AI clusters.

Most important paper of the day

OpenURMA: A Clean-Room Open Implementation of the Unified Bus Protocol

Authors & affiliations: Bojie Li (Pine AI).

Tags: RDMA/RoCE alternatives, NIC architecture, Heterogeneous AI infrastructure

Why this is the top pick: This is the strongest network-facing paper today because it attacks the abstraction boundary that limits current RDMA stacks: per-connection NIC state plus PCIe-mediated work queues. If even part of the Unified Bus argument holds, it changes how we should think about AI-cluster transport endpoints around NPUs/GPUs, not just how we tune congestion control above them.

Deeper explanation: The paper frames RoCE and InfiniBand latency/state overhead as consequences of a Queue-Pair-over-PCIe model. Unified Bus instead splits per-application endpoint state from per-host transport state, places the controller on the on-chip bus, and exposes ordering as an opt-in property. OpenURMA is a clean-room implementation across synthesizable RTL on an Alveo U50, a cycle-level SystemC simulator, and a gem5 scaffold, with matched OpenRoCE baselines. On a 64-byte remote fetch, the reported UB load/store path is about 500 ns end-to-end versus 2186 ns for the matched RoCEv2 RC baseline, with 2.80× higher throughput and modest FPGA resource use. The numbers are from a prototype rather than production silicon, but the architectural claim is the part worth reading: moving the transport endpoint closer to the CPU/NPU fabric may remove costs software-only RDMA tuning cannot.

  • Problem: Modern RDMA endpoints accumulate per-application/per-peer Queue Pair state and pay multiple PCIe crossings for tiny remote operations, which is painful for high-fanout AI and heterogeneous accelerator deployments.
  • Key contributions: A clean-room UB transport/transaction implementation; matched RTL/SystemC/gem5 evaluation harnesses; a controlled comparison against an OpenRoCE-style baseline.
  • Why it matters architecturally: It suggests a hardware/software co-design path where the accelerator or host fabric exposes remote memory as a lower-latency load/store path, while keeping transport state scalable.
  • Useful diagram: Figures 1–4 are especially useful. Figure 1 summarizes the three architectural moves; Figure 4 shows the small-read datapath and why avoiding four PCIe crossings is the claimed latency win.
New arXiv CS submission · RDMA alternatives / transport endpoint design / on-chip bus

OpenURMA: A Clean-Room Open Implementation of the Unified Bus Protocol

Authors & affiliations: Bojie Li (Pine AI)

Tags: RDMA/RoCE alternatives, NIC architecture, Heterogeneous AI infrastructure

Problem: RoCE/InfiniBand-style RDMA keeps the NIC behind PCIe and binds state to application/remote-endpoint Queue Pairs, creating both high tiny-operation latency and poor endpoint-state scaling.

Key contributions from the authors:

  • Implements the public Unified Bus transport and transaction layers in clean-room form across RTL, SystemC, and gem5 tiers.
  • Shows how splitting Jetty-like per-application state from per-host transport-channel state changes connection context growth from multiplicative to additive.
  • Reports about 500 ns for a 64-byte remote LOAD path versus 2186 ns for the matched RoCEv2 RC baseline, plus 2.80× higher throughput in the prototype comparison.

Why it matters: For AI clusters, endpoint scaling and sub-microsecond control/data movement increasingly matter across GPUs, NPUs, CPUs, and memory expanders. This paper is relevant because it questions whether the RNIC-as-PCIe-peripheral model is the right primitive for that world.

Key insights:

  • Some RDMA overheads are architectural, not just implementation artifacts; doorbell batching and better polling do not remove the peripheral boundary.
  • Separating application endpoint state from host-to-host transport state is a direct attack on fanout pressure in large jobs.
  • Opt-in ordering is attractive for AI communication because not every remote memory operation needs strict RC-style ordering.
  • The prototype should be read as a research vehicle, but the abstraction critique is broadly applicable to future NPU/GPU fabrics.

Actionable lessons: When evaluating future accelerator interconnects or SmartNIC/DPU roadmaps, ask where transport state lives, whether tiny remote operations cross PCIe, and which ordering guarantees are paid by default. Benchmark 64B–4KB operations separately from streaming bandwidth.

Useful diagram: Figure 4 cleanly contrasts the work-queue-driven RoCE small-read path with the UB load/store path; Figure 3 shows the O(N·M) versus O(N+M) state model.

New arXiv CS submission · MoE serving / operator disaggregation / network simulation

How Far Can Disaggregation Go? A Design-Space Exploration of Attention-FFN Disaggregation for Efficient MoE LLM Serving

Authors & affiliations: Hanjiang Wu, Abhimanyu Rajeshkumar Bambhaniya, Sarbartha Banerjee, Tuhin Khare, William Won, Tushar Krishna (Georgia Institute of Technology; Infravana); Sudarshan Srinivasan, Souvik Kundu, Madhu Kumar, Midhilesh Elavazhagan (Intel); Suvinay Subramanian (Google); Amir Yazdanbakhsh (Google DeepMind).

Tags: LLM serving, Disaggregated inference, AI cluster networking

Problem: MoE serving now has multiple disaggregation layers — chunked prefill, prefill/decode, and attention–FFN disaggregation — but the payoff depends on workload shape, SLOs, resource split, and interconnect topology.

Key contributions from the authors:

  • Performs a multi-dimensional design-space exploration across token-level parallelism, P/D disaggregation, and attention–FFN disaggregation.
  • Builds AIC++, combining on-device kernel measurements with high-fidelity network simulation for scaled-out disaggregated inference systems.
  • Reports that AFD-attention variants can make strict-SLO DeepSeek-V3.2 serving feasible on 128× B200 and sustain roughly 4k tokens/s where non-AFD deployments are infeasible.

Why it matters: This is a practical map for when deeper disaggregation is actually worth the extra cross-GPU traffic. It directly touches the infrastructure question: can the network absorb finer-grained operator placement, or does disaggregation just move the bottleneck?

Key insights:

  • Attention and FFN have different memory/compute profiles, so separating them can improve GPU memory allocation and SLO feasibility.
  • AFD is not a universal win; the best attention-to-FFN GPU ratio depends on prompt/output lengths, prefix reuse, model architecture, and latency target.
  • Network topology matters because AFD introduces frequent attention-to-FFN and FFN-to-attention transfers that should stay on the highest-bandwidth tier when possible.
  • The paper’s use of packet-granularity network simulation is a good sign; simple bandwidth-only models would miss congestion and placement effects.

Actionable lessons: Treat disaggregated serving as a joint placement-and-transport problem. For AFD-like deployments, profile the A2F/F2A traffic matrix, bind frequent transfers inside the scale-up domain, and search the attention/FFN GPU ratio per workload rather than using a fixed split.

Updated arXiv CS paper · production training / B200 cluster / RoCE storage path

From Detection to Recovery: Operational Analysis on LLM Pre-training with 504 GPUs

Authors & affiliations: Daemyung Kang, Eunjin Hwang, Hanjeong Lee, HyeokJin Kim, Hyunhoi Koo, Jeongkyu Shin, Jeongseok Kang, Jihyun Kang, Joongi Kim, Junbum Lee, Jungseung Yang, Kyujin Cho, Youngsook Song (listed as Lablup Inc. in the arXiv PDF; operational setting includes SKT, Upstage, Lablup, NVIDIA Korea, and VAST Data).

Tags: AI cluster operations, Reliability/observability, Storage-network bottlenecks

Problem: Public production evidence for large AI training failure modes is scarce, especially evidence that connects GPU failures, checkpoint I/O, node exclusions, retry policy, and shared monitoring across organizations.

Key contributions from the authors:

  • Analyzes 55 days of Prometheus metrics and 73 days of operational logs from a 63-node NVIDIA B200 cluster with 504 GPUs.
  • Studies 10 XID-identified GPU failures, 523 checkpoint events, and 224 multi-node training sessions.
  • Identifies a checkpoint “bandwidth paradox”: only 1.4–10.4% utilization of 200 Gbps RoCE bandwidth, attributed to saturation of a 128-slot NFS RPC layer rather than the fabric itself.

Why it matters: This is less about a new transport and more about operational truth. It shows how a nominally fast RoCE/storage path can be bottlenecked by middleware slots and how failure handling needs multi-signal observability rather than one magic GPU metric.

Key insights:

  • No single Prometheus metric dominated across GPU failure types, which argues for multi-signal precursor detection.
  • Checkpointing performance must be traced end-to-end from GPU VRAM through the filesystem/RPC layer to storage, not inferred from link speed.
  • The top 3 of 63 nodes accounted for more than half of node exclusions, suggesting skewed hardware or integration issues can dominate cluster pain.
  • Automatic retry chains achieved a higher reported success rate than manual recovery, but the success rate was still only 33.3%, so recovery automation remains a hard systems problem.

Actionable lessons: For training superpods, build checkpoint-path telemetry that includes RPC slots, NFS/client queues, NIC counters, and storage-side saturation. For failure triage, rank nodes by repeated exclusion and correlate XID, DCGM, OS, fabric, and storage symptoms before blaming the network.

Useful diagram: Figure 1 shows the NUMA-aware resource allocation and gang-scheduling model; Figures 2–4 show concrete GPU/XID precursor timelines, useful for observability design.

Recent arXiv CS paper · MoE AlltoAll / expert-parallel imbalance / benchmarking

Diagnosing Overhead in Dispatch Operations: Cross-architecture Observatory

Authors & affiliations: Bole Ma, Jan Eitzinger, Harald Köstler, Gerhard Wellein (Erlangen National High-Performance Computing Center, NHR@FAU, Erlangen, Germany).

Tags: MoE communication, AlltoAll characterization, AI cluster benchmarking

Problem: MoE expert parallelism is often bottlenecked by AlltoAll dispatch, but many proposed mitigations assume imbalance can be fixed by system placement and that mock-token benchmarks represent production routing.

Key contributions from the authors:

  • Introduces DODOCO, an observatory for measuring MoE dispatch imbalance across architectures and data conditions.
  • Measures five MoE checkpoints spanning MLA, MHA, GQA, Mamba-2, and GDN sequence-mixer designs across EP degrees from 4 to 32 ranks on H100s.
  • Finds that EP scaling changes per-expert max/mean token ratio by at most about 5% in the measurable range, while mock-token inputs can overestimate routing Gini by up to 2.35×.

Why it matters: This is a useful warning for interconnect and collective work: if the model’s router intrinsically concentrates tokens, topology-aware placement alone may not erase the straggler. Also, random/mock token benchmarks can make the network problem look different from real text.

Key insights:

  • The AlltoAll straggler can be rooted in model routing, not just in where experts land on ranks.
  • Different sequence-mixer families form stable imbalance bands; MHA/Mamba-2 were more data-resilient, while MLA/GDN stayed more concentrated in the authors’ measurements.
  • Mock tokens are dangerous for systems conclusions because they can fabricate batch-size scaling trends that disappear with real text.
  • For MoE network design, workload characterization should include per-expert token distributions, not just aggregate bytes.

Actionable lessons: Before optimizing MoE collectives or topology, benchmark with real prompt distributions and report routing Gini/max-mean token ratios across EP sizes. Treat synthetic token tests as stress tests, not as production proxies.

Diagram note: I did not find an obvious architecture diagram in the extracted PDF text; the value is mainly in the measurement tables/plots rather than a system-block diagram.

Recent arXiv CS paper · MoE serving / dynamic context parallelism / KV placement

NanoCP: Request-Level Dynamic Context Parallelism for Data-Expert Parallel Decoding

Authors & affiliations: Jiefei Chen, Binbin Lin, Jinming Ma, Haojie Duanmu, Hao Liu, Qinxiu Cheng, Zhilin Pei, Hui Wang, Xingcheng Zhang, Dahua Lin (Shanghai Artificial Intelligence Laboratory and affiliated institutions); Jiangfei Duan (The Chinese University of Hong Kong); Xiuhong Li (Peking University); additional affiliations listed in the PDF include Fudan University, Huazhong University of Science and Technology, Shanghai Jiao Tong University, Harbin Institute of Technology, SenseTime, and The Chinese University of Hong Kong.

Tags: LLM serving, MoE communication, KV-cache placement

Problem: Hybrid data-expert-parallel MoE serving binds each request’s attention, MoE communication, and KV cache to one instance, which creates both EP stragglers and KV memory fragmentation under variable-length workloads.

Key contributions from the authors:

  • Identifies rigid request-to-instance binding as a root cause of dispatch/combine stragglers and memory imbalance.
  • Proposes NanoCP, a dynamic context-parallelism system assigning per-request CP degrees while decoupling MoE communication from KV cache placement.
  • Reports up to 3.27× higher sustainable request rate and 1.79×–2.12× lower P99 normalized latency versus state-of-the-art baselines under strict TPOT SLOs.

Why it matters: NanoCP is not a pure networking paper, but it is network-adjacent in the right way: it changes which tensors move between instances and when asymmetric transfers leave the collective path.

Key insights:

  • Long-context requests need more attention parallelism, but applying uniform CP to every request wastes communication on short requests.
  • Per-request CP creates asymmetric cross-instance traffic, so the communication backend matters as much as the scheduling policy.
  • The system pairs an ahead-of-time static-shape graph manager with routing-based communication to work around CUDA Graph and DeepEP constraints.
  • The core design lesson is to decouple KV locality from MoE batch balance instead of overloading one placement decision with both goals.

Actionable lessons: In MoE serving schedulers, track KV-cache placement and expert dispatch pressure as separate resources. If per-request context parallelism is used, model the asymmetric transfer matrix explicitly and keep those transfers off the slowest inter-node paths where possible.

Fast take

The day’s theme is abstraction boundaries: OpenURMA moves the transport endpoint, AFD and NanoCP move serving operators/KV state, the B200 report exposes where the storage path really stalls, and DODOCO reminds us that MoE communication skew often starts inside the model router.
