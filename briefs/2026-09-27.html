Most important paper of the day

HeteroReason: Heterogeneous FPGA-GPU Acceleration for Disaggregated Speculative Reasoning

Authors & affiliations: Zehuan Zhang, Quan Deng, Zhibo Ren, Hao Mark Chen, Guoyu Li, Xuchun Hu, Jose G. F. Coutinho, Ce Guo, Wayne Luk, Zhiqiang Que, Hongxiang Fan — Imperial College London; Tsinghua University; University of Bristol.

Tags: Heterogeneous AI Infrastructure, FPGA-GPU Serving, Prefill-Decode Disaggregation

Why this is the top pick: This is the strongest signal today because it treats heterogeneous serving as a pipeline/data-movement problem, not just an accelerator-placement problem. The specific network angle is local rather than datacenter-scale, but the system pattern is very relevant: disaggregate execution stages, hide synchronization, and make rollback/state movement explicit.

Deeper explanation: HeteroReason is useful because the performance problem is framed as cross-device state movement and schedule overlap. The FPGA does the lightweight draft path; GPUs handle PRM and target refinement; the system then has to keep reasoning state coherent while allowing rollback and step-ahead execution. For Ethan’s world, the general lesson is that a heterogeneous AI fabric is only as good as its synchronization protocol. If the handoff is token-granular and blocking, the accelerator boundary becomes the bottleneck; if the system can pipeline, shadow-sync, and recover, the boundary becomes a useful partition.

  • Problem: Speculative reasoning for large reasoning models mixes several execution modes: sequential draft-token generation, PRM-style verification, target-model refinement, rollback/backtracking, and synchronization between stages. Running all of that on homogeneous GPUs can underutilize resources and expose synchronization latency.
  • Key contributions:
  • Proposes HeteroReason, an algorithm-hardware co-design that maps the draft model to FPGA while keeping PRM and target-model refinement on GPUs.
  • Adds a backtracking-enhanced reasoning workflow so the system can recover from poor intermediate reasoning states rather than following a strictly forward-only path.
  • Introduces shadow synchronization plus step-ahead speculation/refinement scheduling to overlap FPGA token updates with GPU-side refinement; reports 1.01×–1.42× latency speedups and 1.25×–1.57× energy-efficiency improvements over homogeneous GPU baselines.
  • Why it matters architecturally: When designing heterogeneous AI serving, model state synchronization and rollback as first-class traffic. Accelerator partitioning only helps if the handoff protocol keeps the critical path short; otherwise the fabric boundary eats the speedup. Treat “prefill/decode disaggregation” as a family of state-consistency contracts, not just a deployment topology.

HeteroReason: Heterogeneous FPGA-GPU Acceleration for Disaggregated Speculative Reasoning

Authors & affiliations: Zehuan Zhang, Quan Deng, Zhibo Ren, Hao Mark Chen, Guoyu Li, Xuchun Hu, Jose G. F. Coutinho, Ce Guo, Wayne Luk, Zhiqiang Que, Hongxiang Fan — Imperial College London; Tsinghua University; University of Bristol.

Tags: Heterogeneous AI Infrastructure, FPGA-GPU Serving, Prefill-Decode Disaggregation

Problem: Speculative reasoning for large reasoning models mixes several execution modes: sequential draft-token generation, PRM-style verification, target-model refinement, rollback/backtracking, and synchronization between stages. Running all of that on homogeneous GPUs can underutilize resources and expose synchronization latency.

Key contributions from the authors:

  • Proposes HeteroReason, an algorithm-hardware co-design that maps the draft model to FPGA while keeping PRM and target-model refinement on GPUs.
  • Adds a backtracking-enhanced reasoning workflow so the system can recover from poor intermediate reasoning states rather than following a strictly forward-only path.
  • Introduces shadow synchronization plus step-ahead speculation/refinement scheduling to overlap FPGA token updates with GPU-side refinement; reports 1.01×–1.42× latency speedups and 1.25×–1.57× energy-efficiency improvements over homogeneous GPU baselines.

Why it matters: This is the strongest signal today because it treats heterogeneous serving as a pipeline/data-movement problem, not just an accelerator-placement problem. The specific network angle is local rather than datacenter-scale, but the system pattern is very relevant: disaggregate execution stages, hide synchronization, and make rollback/state movement explicit.

Key insights:

  • The interesting systems move is not “FPGA is faster”; it is matching draft, verify, and refine phases to different execution substrates while preserving a coherent reasoning state.
  • Shadow synchronization is a useful abstraction for any heterogeneous fabric: keep a stale-enough-but-safe state on the other side so the fast path does not block on every token/state update.
  • Backtracking makes the control plane more complex because rollback is no longer an exceptional failure case; it becomes part of the normal scheduling path.
  • Step-ahead scheduling turns a nominally sequential decode/refine loop into a pipeline, which is exactly the kind of transformation that exposes fabric and synchronization bottlenecks.

Actionable lessons: When designing heterogeneous AI serving, model state synchronization and rollback as first-class traffic. Accelerator partitioning only helps if the handoff protocol keeps the critical path short; otherwise the fabric boundary eats the speedup. Treat “prefill/decode disaggregation” as a family of state-consistency contracts, not just a deployment topology.

HBF-Sim: An Extensible HBF Simulator for Large-scale GPU Memory Systems

Authors & affiliations: Yaqi Li, Jing Wang, Junfeng Wang, Long Yang, Han Yan, Xiaohu Chai, Liang Shi — East China Normal University; Shanghai Innovation Institute.

Tags: GPU Memory Systems, High-Bandwidth Flash, LLM Infrastructure

Problem: High-bandwidth flash is being positioned as a package-local capacity tier for GPUs, but it is neither HBM nor NVMe. Existing GPU and SSD simulators miss the full request path: GPU cache-line accesses, page granularity, channel-affine NAND resources, queuing, backpressure, and completion behavior.

Key contributions from the authors:

  • Builds HBF-Sim, an extensible simulator integrated with simulated GPUs to model the GPU–HBF request/completion path end to end.
  • Separates the GPU–HBF interaction controller from the page-based parallel stack storage, exposing address mapping, request merging, channel placement, NAND service, and queueing effects.
  • Uses validation tests and microbenchmarks to show bottlenecks from channel distribution, resource conflicts, write aggregation, and read/write interference.

Why it matters: This matters because HBF-style tiers keep appearing in KV-cache and long-context serving designs. If the simulator treats HBF as “big HBM” or “fast SSD,” it will overestimate usable bandwidth and miss exactly the contention modes that determine whether the tier is viable.

Key insights:

  • The 64 B GPU cache-line to 4 KiB NAND-page mapping is the core impedance mismatch; bandwidth depends on coalescing and placement, not just interface peak rate.
  • Channel placement policy matters: contiguous, grouped, and interleaved mappings expose different page-service amplification and conflict behavior.
  • Read/write isolation and admission timing can change tail latency, which is critical for decode paths that cannot hide long stalls.
  • For cluster-scale planning, HBF changes the local memory hierarchy, but the same modeling lesson applies to network tiers: simulate the real request granularity and queueing point, not just the nominal link bandwidth.

Actionable lessons: For KV-cache/offload architecture work, demand an end-to-end path model before trusting capacity-tier speedups. Track request granularity conversion, queue occupancy, completion latency, and conflict domains. A cheap but faithful simulator is better than a beautiful spreadsheet with peak TB/s numbers.

Xtrace: High-Fidelity GPU Intra-Kernel Tracing via Binary-Level Instruction Splicing

Authors & affiliations: Zhuobin Huang, Kai Zhang, Weihao Cui, Hongshi Tan, Liang Luo, Christopher Dewan, Shen Li, Bingsheng He — National University of Singapore; Meta.

Tags: GPU Observability, LLM Kernels, Performance Tooling

Problem: Modern LLM kernels fuse memory access, compute, and sometimes communication-related behavior into a single kernel. Existing tracing tools insert probes before compilation, which changes the optimized binary being measured and can add enough overhead to distort the performance signal.

Key contributions from the authors:

  • Introduces Xtrace, a GPU intra-kernel tracing system that splices probes directly into the compiled binary, avoiding compile-time interference.
  • Reuses only dead-value registers at insertion points and resolves hazards using compiler hazard tables; supports 19 NVIDIA and AMD GPU architectures.
  • Evaluates on production LLM kernels across H100, B300, and MI300X, preserving 94–98% binary similarity with 0.9–2.8% overhead and using traces to guide FlashAttention optimization.

Why it matters: This is observability rather than networking, but it is still useful AI infrastructure signal. For collective overlap, fused kernels, and GPU-side data movement, bad tracing can create phantom bottlenecks. Xtrace is a reminder that measurement tooling must preserve the binary and timing regime it claims to explain.

Key insights:

  • Binary-level instrumentation is valuable because source-level or IR-level probes can perturb compiler scheduling, register allocation, and fusion decisions.
  • The paper’s comparison metric is the right instinct: fidelity is not only overhead; it is also how much of the original instruction stream survives.
  • For kernel-autotuning agents, trace quality changes the search trajectory; noisy traces waste optimization iterations.
  • This is relevant to communication/computation overlap studies because the critical events are often inside large fused kernels where aggregate counters are too coarse.

Actionable lessons: When diagnosing AI workloads, validate the observer effect. If instrumentation changes register pressure, scheduling, or kernel structure, the trace may explain the instrumented program rather than the deployed one. Prefer profiling paths that report binary similarity/fidelity, not only overhead.

When Fancy Eviction Fails: Rethinking Cache Replacement For LLM Prefix Reuse

Authors & affiliations: Yiyu Liu, Minlan Yu, Juncheng Yang — Harvard University.

Tags: LLM Serving, Prefix/KV Cache, Memory Hierarchy

Problem: Long-running agentic LLM sessions repeatedly send growing context. Prefix caching avoids recomputing shared prefixes, but production prefix-cache workloads do not necessarily behave like traditional web/block-cache traces, so fancy eviction policies may optimize the wrong signal.

Key contributions from the authors:

  • Studies production traces from two organizations and evaluates 14 eviction algorithms across HBM-constrained and large memory-pool settings.
  • Finds that sophisticated traditional cache policies provide little improvement over LRU because active sessions create regular, recency-dominated reuse.
  • Introduces compute-savings ratio and offline oracles, then recommends LRU-like retention with quick demotion for one-hit prefixes, compute-aware partial eviction, and capacity-dependent eviction granularity.

Why it matters: This is not a fabric paper, but it directly affects disaggregated serving designs: prefix/KV cache placement determines how much data moves across GPU memory, host memory, SSD/CXL pools, or network-attached cache. The key message is practical: hit ratio alone is not the right objective when miss cost grows with token depth.

Key insights:

  • Recency is unusually predictive because session progress is paced; frequency is better used for admission/demotion than for ranking long-lived cached prefixes.
  • A few large sessions dominate bytes, so all-or-nothing eviction can waste capacity or trigger large recomputation bursts.
  • Hit ratio and compute saved can diverge sharply; a late-depth miss may be far more expensive than many shallow misses.
  • For tiered/disaggregated cache systems, eviction granularity should change with the tier: block-level in scarce HBM, coarser decisions in larger pools.

Actionable lessons: For LLM serving cache design, optimize bytes × recompute cost × transfer path, not hit ratio alone. If KV/prefix state crosses a network or CXL/SSD boundary, cache policy becomes a data-movement policy; track miss-cost distribution and fragmentation explicitly.
