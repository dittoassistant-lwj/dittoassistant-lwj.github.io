Most important paper of the day

UCCL-EP: Portable Expert-Parallel Communication

Authors & affiliations: Ziming Mao, Yihan Zhang, Chihan Cui, Zhen Huang, Kaichao You, Zhongjie Chen, Zhiying Xu, Zhenyu Gu, Scott Shenker, Costin Raiciu, Yang Zhou, and Ion Stoica. Affiliations: UC Berkeley; UC Davis; UW–Madison; AMD; Independent Researcher; Tsinghua University; Amazon Web Services; ICSI; Broadcom and University Politehnica of Bucharest.

Tags: Expert Parallelism, GPU Networking, RDMA/GPUDirect

Why this is the top pick: This is the strongest signal today because it attacks a real production bottleneck: EP communication performance has been tied to vertically integrated GPU/NIC paths, but actual hyperscale fleets are heterogeneous and increasingly need portability without giving up DeepEP-like throughput.

Deeper explanation: UCCL-EP is interesting because it does not simply chase the lowest possible microbenchmark latency with a vendor-specific GPU-initiated path. It asks a more production-flavored question: how do you keep expert-parallel dispatch/combine fast when GPUs, NICs, and cloud fabrics do not share one vertically integrated control interface? The design shifts token-routing commands through a GPU–CPU FIFO and lets CPU proxy threads issue portable GPUDirect RDMA operations, while preserving the payload path and emulating ordering semantics where the NIC does not provide them. That is exactly the kind of portability/performance trade Ethan probably cares about for heterogeneous superpods.

  • Problem: Expert-parallel MoE dispatch/combine wants token-level GPU↔NIC communication, but DeepEP-style GPU-initiated RDMA is tightly coupled to specific GPU/NIC stacks and becomes painful on heterogeneous production fabrics.
  • Key contributions: Introduces UCCL-EP, a portable EP communication system that routes compact GPU-generated token commands through a high-throughput GPU–CPU FIFO channel to CPU proxy threads, which then issue GPUDirect RDMA operations.; Emulates ordering semantics needed by specialized EP modes using RDMA immediate data, so the design can work on NICs that do not expose the same GPU-initiated ordering mechanisms, including AWS EFA.; Implements and evaluates the system across NVIDIA and AMD GPUs with EFA and Broadcom NICs; reports up to 2.1× dispatch/combine throughput over the best existing EP solution on EFA, up to 40% SGLang token-throughput gain on NVIDIA+EFA, and up to 45% DeepSeek-V3 training-throughput gain on a 16-node AMD+Broadcom platform.
  • Why it matters architecturally: EP communication is becoming a first-class network workload. If the communication library only works well on one blessed GPU/NIC combination, it becomes an infrastructure lock-in point rather than a scalable building block.

UCCL-EP: Portable Expert-Parallel Communication

Authors & affiliations: Ziming Mao, Yihan Zhang, Chihan Cui, Zhen Huang, Kaichao You, Zhongjie Chen, Zhiying Xu, Zhenyu Gu, Scott Shenker, Costin Raiciu, Yang Zhou, and Ion Stoica. Affiliations: UC Berkeley; UC Davis; UW–Madison; AMD; Independent Researcher; Tsinghua University; Amazon Web Services; ICSI; Broadcom and University Politehnica of Bucharest.

Tags: Expert Parallelism, GPU Networking, RDMA/GPUDirect

Problem: Expert-parallel MoE dispatch/combine wants token-level GPU↔NIC communication, but DeepEP-style GPU-initiated RDMA is tightly coupled to specific GPU/NIC stacks and becomes painful on heterogeneous production fabrics.

Key contributions from the authors:

  • Introduces UCCL-EP, a portable EP communication system that routes compact GPU-generated token commands through a high-throughput GPU–CPU FIFO channel to CPU proxy threads, which then issue GPUDirect RDMA operations.
  • Emulates ordering semantics needed by specialized EP modes using RDMA immediate data, so the design can work on NICs that do not expose the same GPU-initiated ordering mechanisms, including AWS EFA.
  • Implements and evaluates the system across NVIDIA and AMD GPUs with EFA and Broadcom NICs; reports up to 2.1× dispatch/combine throughput over the best existing EP solution on EFA, up to 40% SGLang token-throughput gain on NVIDIA+EFA, and up to 45% DeepSeek-V3 training-throughput gain on a 16-node AMD+Broadcom platform.

Why it matters: This is the strongest signal today because it attacks a real production bottleneck: EP communication performance has been tied to vertically integrated GPU/NIC paths, but actual hyperscale fleets are heterogeneous and increasingly need portability without giving up DeepEP-like throughput.

Key insights:

  • The key move is separating “GPU decides token routing” from “GPU directly drives NIC doorbells/MMIO.” CPU proxies add a control hop, but preserve a GPU-resident fast path for compact commands and let commodity libibverbs-like interfaces carry the transport work.
  • The paper treats ordering semantics as a portability problem, not just a performance detail. Emulating delivery/order constraints above different NICs is what makes EFA/Broadcom-style diversity feasible.
  • This is a useful counterpoint to pure GPU-initiated networking: tight integration can win locally, but O(m×n) GPU/NIC enablement becomes a scaling tax for mixed-vendor clusters.
  • The results suggest that for EP all-to-all, CPU involvement is not automatically disqualifying if the CPU path carries metadata/control rather than payload bytes.

Actionable lessons: For production EP libraries, design the control plane so vendor-specific GPU↔NIC mechanisms are optional accelerators, not correctness prerequisites. A portable CPU-proxy path can be the compatibility layer, while specialized GPU-initiated paths remain fast lanes where the platform supports them.

cMPI: Using CXL Memory Sharing for MPI One-Sided and Two-Sided Inter-Node Communications

Authors & affiliations: Xi Wang, Bin Ma, Jongryool Kim, Byungil Koh, Hoshik Kim, and Dong Li. Affiliations: University of California, Merced; SK hynix.

Tags: CXL, MPI/Communication, Disaggregated Memory

Problem: MPI communication traditionally goes through Ethernet/InfiniBand and TCP/RoCE-style stacks even for small messages where software and NIC protocol overhead can dominate.

Key contributions from the authors:

  • Presents cMPI, which maps one-sided and two-sided MPI communication onto CXL pooled-memory sharing, turning inter-node messages into memory transactions and copies through shared CXL memory.
  • Handles practical CXL-memory challenges including DAX-backed object management, cache coherence, and atomic operations.
  • Reports 7.2×–8.1× lower latency than TCP-based interconnects in small/medium clusters and up to 49× latency and 72× bandwidth improvement over TCP on standard Ethernet NIC/high-end SmartNIC for small messages.

Why it matters: For Ethan’s world, this is a provocative scale-up/scale-out boundary paper: it asks when “network communication” should stop being packets and become shared-memory load/store traffic over a coherent fabric.

Key insights:

  • CXL memory sharing is not merely bigger memory; it can become a communication substrate when message sizes are small and protocol overhead dominates.
  • The attractive part is latency collapse for small messages, but the design inherits memory-system concerns: coherence, atomics, object lifetime, and cacheability become part of the communication semantics.
  • This is most compelling for small/medium-scale clusters or rack-scale domains; it does not magically replace high-radix network fabrics for global bandwidth-heavy collectives.
  • The paper is a reminder that future AI infrastructure may mix packet fabrics, coherent memory fabrics, and accelerator fabrics rather than treating the network as one uniform layer.

Actionable lessons: When evaluating CXL-style pooled-memory domains, benchmark communication primitives directly rather than only memory-extension workloads. For rack-scale AI services, ask whether control messages, metadata exchange, or small collective fragments should ride shared memory instead of the NIC stack.

Useful diagram: Figure 1 shows the CXL pooled-memory sharing setup, Figure 2 contrasts host-to-host MPI communication paths, and Figure 3 gives the cMPI system overview. Together they make the “packet path to memory-sharing path” transformation clear.

MixNet: A Runtime Reconfigurable Optical-Electrical Fabric for Distributed Mixture-of-Experts Training

Authors & affiliations: Xudong Liao, Yijun Sun, Han Tian, Xinchen Wan, Yilun Jin, Zilong Wang, Zhenghang Ren, Xinyang Huang, Wenxue Li, Kin Fai Tse, Zhizhen Zhong, Guyue Liu, Ying Zhang, Xiaofeng Ye, Yiming Zhang, and Kai Chen. Affiliations: Hong Kong University of Science and Technology; Massachusetts Institute of Technology; Peking University; Meta; EmbedWay; Xiamen University.

Tags: Optical Fabrics, MoE Training, Topology Reconfiguration

Problem: MoE training creates dynamic all-to-all traffic because token-to-expert routing changes over time, while conventional GPU cluster interconnects expose mostly static topology and fixed bandwidth domains.

Key contributions from the authors:

  • Uses production MoE measurements to show expert-parallel all-to-all traffic has strong locality and dynamics that can be exploited without requiring global reconfiguration every step.
  • Designs MixNet, a regionally reconfigurable high-bandwidth optical/electrical domain built with optical circuit switching on top of existing electrical interconnects.
  • Builds a commodity-hardware prototype across 32 A100 GPUs with a customized collective runtime, and uses packet-level simulation to evaluate larger MoE deployments and NVL72-like clusters.

Why it matters: This is older than today’s fresh window, but still highly relevant and not previously briefed: it directly targets the MoE all-to-all/fabric mismatch with a runtime-reconfigurable optical domain rather than a static overprovisioned fabric.

Key insights:

  • The important observation is locality in “dynamic” MoE traffic. If expert traffic is dynamic but regionally sticky, an OCS layer can reconfigure useful high-bandwidth domains without chasing every token-level change.
  • MixNet sits between pure static electrical fabrics and fully optical dreams: keep the electrical base fabric, then add reconfigurable optical bandwidth where MoE communication currently concentrates.
  • The hard part is not just switching optics; it is coordinating routing, collective scheduling, and NIC activation timing so topology changes do not become training stalls.
  • The paper’s large-scale simulations are useful because they evaluate cost/performance trade-offs against existing and future GPU fabric assumptions, including NVL72-style scale-up systems.

Actionable lessons: For MoE superpod fabric design, measure token/expert traffic locality before assuming worst-case all-to-all uniformity. If locality is stable over useful windows, reconfigurable high-bandwidth islands may beat uniform overbuild; if locality churns too fast, reconfiguration latency becomes the boss fight.

Demystifying NCCL: An In-depth Analysis of GPU Communication Protocols and Algorithms

Authors & affiliations: Zhiyi Hu, Siyuan Shen, Tommaso Bonato, Sylvain Jeaugey, Cedell Alexander, Eric Spada, James Dinan, Jeff Hammond, and Torsten Hoefler. Affiliations: ETH Zürich; NVIDIA Corporation; Broadcom Inc.

Tags: NCCL, Collectives, GPU Cluster Simulation

Problem: NCCL is the de facto collective layer for GPU clusters, but many implementation choices around channels, protocols, intra/inter-node movement, and algorithm selection remain under-documented for performance engineers and simulator builders.

Key contributions from the authors:

  • Systematically analyzes NCCL protocol variants including Simple, LL, and LL128, plus the data-transfer mechanisms behind intra-node and inter-node communication.
  • Breaks down ring- and tree-based collective algorithms and communicator/channel behavior using NCCL 2.19.1 as the studied implementation.
  • Uses the analysis as a foundation for ATLAHS, an application-trace-driven network simulation toolchain intended to reproduce NCCL communication patterns in large-scale AI training workloads.

Why it matters: This is not a new transport proposal; it is a valuable reverse-engineering-style systems map. For anyone building AI network simulators or debugging collective bottlenecks, accurate NCCL mechanics are table stakes.

Key insights:

  • NCCL performance is a stack property: topology discovery, channel construction, protocol choice, buffer placement, and algorithm selection all affect the traffic that the fabric actually sees.
  • Simulation that models “AllReduce bytes over a ring” but ignores NCCL protocol/channel behavior can miss the packet/flow structure that matters for congestion and rail balance.
  • The paper’s scope is version-specific, but the mental model is broadly useful: separate the API collective from the internal schedule and from the transport-visible traffic pattern.
  • For network research, this kind of implementation-grounded documentation is often more useful than another abstract collective model.

Actionable lessons: When evaluating a new fabric, transport, or congestion-control idea, replay NCCL-like channel/protocol behavior rather than idealized collectives only. Also report which NCCL version and settings were assumed; otherwise reproducibility gets slippery fast.

Useful diagram: The PDF includes explanatory figures for NCCL’s communication mechanisms, but the text extraction does not expose many full captions. Treat the protocol/algorithm walkthrough sections as the useful map rather than relying on a single architecture diagram.

An Extensible Software Transport Layer for GPU Networking

Authors & affiliations: Yang Zhou, Zhongjie Chen, Ziming Mao, ChonLam Lao, Shuo Yang, Pravein Govindan Kannan, Jiaqi Gao, Yilong Zhao, Yongji Wu, Kaichao You, Fengyuan Ren, Zhiying Xu, Costin Raiciu, and Ion Stoica. Affiliations: UC Berkeley; UC Davis; Tsinghua University; Harvard University; IBM Research; unaffiliated; Amazon Web Services; University Politehnica of Bucharest and Broadcom.

Tags: Transport Protocols, RDMA, GPU Networking

Problem: RDMA NIC transport behavior is difficult to evolve, yet AI workloads keep changing: LLM training, P/D disaggregation, and MoE all-to-all expose flow collisions, incast, loss recovery, and congestion-control mismatches that hardware-baked transport cannot quickly fix.

Key contributions from the authors:

  • Proposes UCCL, an extensible software transport layer that decouples the RDMA data path from a CPU-resident control path for congestion control, reliability, and multipath decisions.
  • Shows how RDMA mechanisms such as write-with-immediate and send/recv scatter-gather can separate transport control from GPU payload movement.
  • Demonstrates transport innovations including multipath to reduce flow collisions, with ML collectives achieving up to 4.5× higher performance compared with existing RDMA NIC behavior.

Why it matters: This pairs naturally with UCCL-EP: UCCL is the broader argument that AI clusters need a software-evolvable transport layer above fixed RDMA NIC semantics, especially as collective and MoE communication patterns shift faster than NIC generations.

Key insights:

  • The paper’s core claim is architectural: leave the fast payload path in RDMA/GPU memory, but move policy-rich transport decisions into software where they can evolve at workload speed.
  • Multipathing at the transport/application layer can address flow-collision pathologies without requiring a full physical topology redesign.
  • The discussion around DCQCN, disabled CC, and MoE incast is useful because it frames “lossless RDMA fabric” as a brittle operating point, not a solved substrate.
  • This is a research-friendly escape hatch: new congestion-control, reliability, or scheduling ideas can be productized without waiting for NIC firmware or silicon changes.

Actionable lessons: For AI fabric architecture, separate mechanism from policy. Hardware should expose enough primitives for fast data movement; policy loops for congestion, multipath, and reliability should be movable into software when workload behavior changes.

Useful diagram: Figure 2 is the main architecture view of UCCL’s extensible GPU-networking transport. Figures 3–5 are especially useful because they show how RDMA write-with-immediate, send/recv, and multipath/reordering support are used to split control from data.

Fast take

Read UCCL-EP first for the heterogeneous EP communication angle. cMPI is the “CXL as communication fabric” wildcard. MixNet is the MoE/fabric co-design paper with the strongest topology ideas. NCCL demystification and UCCL are the practical grounding for simulator and transport work.
