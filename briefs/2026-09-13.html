verified arXiv paper · Collective Communication, LLM Training, GPU Topology

Compass: Dissecting Communication and Computation Operators for Efficient LLM Training

Authors & affiliations: Guangyu Xiang, Lin Zhang, Haoxuan Yu, Xinglin Pan, Shaohuai Shi, and Xiaowen Chu — The Hong Kong University of Science and Technology (Guangzhou); The Hong Kong University of Science and Technology; Harbin Institute of Technology, Shenzhen.

Tags: Collective Communication, LLM Training, GPU Topology

Problem: Tensor-parallel LLM training spends significant time in collective communication, but existing overlap mechanisms either fuse operators without enough topology awareness or decompose tensors without a reliable way to choose the best pipeline depth. Compass targets the overlap boundary between collectives and GEMM on hybrid NVLink/PCIe multi-GPU systems.

Key contributions from the authors:

  • Introduces a topology-aware IntraFusion method that uses double-ring communication to improve bandwidth utilization in hybrid NVLink–PCIe systems.
  • Develops a model for choosing the tensor decomposition degree in InterDecom, rather than tuning the pipeline depth by trial and error.
  • Builds a unified performance framework that selects between sequential execution, topology-aware fusion, and decomposition; the paper reports up to 1.42× end-to-end speedup over Megatron-LM on evaluated GPT/Llama workloads.

Why it matters: This is the strongest signal today because it sits exactly at the compute/network seam Ethan cares about: not a generic training paper, but a concrete model for when communication-computation overlap actually works on real multi-GPU topology.

Key insights:

  • Overlap is not automatically useful. Intra-operator fusion can lose much of its benefit if its communication pattern underuses the available links or stresses the wrong NUMA boundary.
  • Compass treats collective overlap as a topology problem, not just a kernel scheduling problem. The double-ring design matters because the physical GPU fabric changes the effective bandwidth of the same collective.
  • The decomposition degree for pipelining is workload-dependent: too little decomposition leaves communication exposed; too much adds overhead and fragmentation.
  • The paper usefully separates two regimes: topology-aware fused collectives for bandwidth utilization, and model-guided decomposition for pipeline depth selection.

Actionable lessons: For production superpods, collectives should expose enough topology and workload metadata for runtime strategy selection. A practical CCL/NCCL-adjacent design should decide when to use fused ring-style overlap versus decomposed pipelining based on tensor shape, TP size, and measured interconnect bandwidth rather than a fixed recipe.

ExaServe: Large-Scale LLM Serving on Exascale HPC Systems

Authors & affiliations: Wenyi Wang, Shu Shi, Yadu Babuji, Ian Foster, and Kyle Chard — The University of Chicago; Argonne National Laboratory.

Tags: LLM Serving, HPC/AI Clusters, Control Plane Scaling

Problem: Cloud-native LLM serving stacks are built for data-center service environments, while leadership-class HPC systems use schedulers, MPI launch paths, parallel file systems, and accelerator-specific constraints. ExaServe tries to make large-scale serving reproducible on systems such as ALCF Aurora while exposing where the serving control plane breaks.

Key contributions from the authors:

  • Provides a pip-installable framework that turns a declarative YAML specification into a reproducible LLM serving deployment across HPC nodes.
  • Deploys vLLM/SGLang-style serving on Aurora from 1 to 256 nodes, including MPI launch, accelerator selection, node-local weight staging, and front-end proxy setup.
  • Reports near-linear non-streaming scaling to 256 nodes, but identifies streaming proxy saturation around 4.7k requests/s and an O(N²) Ray Serve control-plane bottleneck that stretches bring-up to roughly 30 minutes at 256 nodes.

Why it matters: This is useful because it surfaces cluster-serving bottlenecks that are not model bottlenecks: front-end streaming, launch orchestration, weight staging, and Ray control-plane behavior. Those are exactly the boring dragons that bite large AI infrastructure.

Key insights:

  • The model servers can remain inside SLO while the centralized streaming proxy becomes the limiter, which means “GPU utilization looks fine” is insufficient evidence that serving is healthy.
  • Non-streaming and streaming paths have different scaling laws. Token streaming creates long-lived response paths that can saturate proxies well before backend replicas saturate.
  • The Ray Serve control-plane issue is a reminder that scale-out serving has two planes: request/data path and deployment/control path. Both need asymptotic sanity.
  • HPC systems add friction points—batch scheduling, MPI launch, shared file systems, node-local staging—that cloud-native serving frameworks usually hide or assume away.

Actionable lessons: When scaling LLM serving, test direct dispatch, proxy fan-out, and control-plane bring-up separately. For large clusters, avoid single centralized streaming choke points, measure deployment time as a first-class metric, and keep weight staging close to nodes instead of assuming the shared file system will behave like local NVMe.

Figures 2–4 are also useful for seeing where streaming diverges from non-streaming at scale.

verified arXiv paper · Edge Inference, MLLM Serving, Communication Compression

EMMI: Edge Multi-Modal Intelligence for Communication-Efficient MLLM Inference via Fused Representation Compression

Authors & affiliations: Motahare Mounesan and Irfan Khan — Texas A&M University.

Tags: Edge Inference, MLLM Serving, Communication Compression

Problem: Edge devices often cannot run full multimodal LLM inference locally, but sending raw sensor/video/text inputs to a server can dominate latency and bandwidth. EMMI moves modality-specific encoding, fusion, and compression to the edge so the network carries a compact latent representation instead of raw observations.

Key contributions from the authors:

  • Proposes an edge–server pipeline that encodes each modality locally, fuses representations, compresses the fused latent, and sends only the compact representation to server-side MLLM reasoning.
  • Uses learned compression to create a fixed-size interface between heterogeneous edge devices and server resources.
  • Reports a 32× payload reduction and up to 3.4× lower estimated end-to-end latency under bandwidth-constrained edge conditions while maintaining comparable downstream accuracy in the evaluated benchmark.

Why it matters: This is not datacenter collective traffic, but it is a clean network-facing AI systems paper: it treats the inference split point as a data-movement interface and shows how representation compression shifts the bottleneck away from the access network.

Key insights:

  • The split point matters. Sending raw multimodal inputs is often wasteful, while splitting at arbitrary neural layers can create unstable or task-specific interfaces.
  • A fused latent representation can become the “wire format” between edge and server, which is an interesting systems abstraction for heterogeneous edge fleets.
  • The latency win comes from moving bytes out of the network path, not from making the server model cheaper. At 0.1 Mbps, transmission dominates without compression.
  • The privacy story is secondary but relevant: local encoding avoids shipping raw observations, though the paper does not prove a strong privacy guarantee.

Actionable lessons: For edge/cloud AI serving, define the network interface explicitly: raw input, intermediate activation, fused latent, or KV/state transfer. Then optimize and budget that interface. In bandwidth-limited paths, reducing payload variance can matter as much as reducing mean payload size.

Useful diagram: Figure 1 is the useful system diagram: it shows edge-side encode/fuse/compress and server-side decompress/reason. Figure 2 breaks down end-to-end latency and shows transmission falling from the dominant component to a much smaller slice under compression.

verified arXiv paper · Heterogeneous Memory, HBM/DRAM Tiering, Runtime Systems

Memory Profiling and Migration for Heterogeneous Memory Architectures

Authors & affiliations: Marios Asiminakis, Polydoros Petrakis, and Manolis Marazakis — Institute of Computer Science, Foundation for Research and Technology – Hellas (FORTH), Heraklion, Greece.

Tags: Heterogeneous Memory, HBM/DRAM Tiering, Runtime Systems

Problem: HBM+DRAM systems promise high bandwidth with larger memory capacity, but page placement is often manual or left to OS heuristics that are not designed for dynamic multi-tier behavior. SHAMBLES profiles memory behavior and migrates data across tiers without application changes.

Key contributions from the authors:

  • Introduces SHAMBLES, a kernel-integrated framework with low-overhead profiling, page migration, and a policy-agnostic interface for heterogeneous memory systems.
  • Provides a user-space runtime with pluggable recency/frequency-style policies plus logging for reproducible allocation and migration timelines.
  • Evaluates HPCG, DGEMM, and Himeno on a Linux system with HBM and DDR exposed as NUMA nodes; reports up to 93.75% of all-HBM HPCG performance while keeping only 40% of the problem size in HBM, and up to 99% of all-HBM DGEMM performance with one-third of the footprint in HBM.

Why it matters: This is adjacent rather than network-native, but still useful for AI infrastructure: tiered HBM/DRAM/CXL-style systems need runtime placement loops, and the same policy questions show up when KV cache, optimizer state, or embeddings spill beyond fast memory.

Key insights:

  • The right “fast tier” is not universal. Himeno shows cases where DDR-as-fast and HBM-as-fast choices can flip depending on size and locality.
  • Migration overhead must be visible. SHAMBLES logs allocation and migration timelines, which is exactly the evidence needed to debug tiering policies.
  • Keeping hot data in HBM can recover most performance with much less HBM capacity, but only if the policy tracks changing locality.
  • The design separates mechanism from policy, which is the right pattern for future CXL/HBM/host-memory AI runtimes.

Actionable lessons: For heterogeneous AI memory, build observability before clever policy. Track per-allocation hotness, migration volume, and fast-tier hit rate; then test policies under changing phase behavior. For KV/optimizer-state tiering, avoid assuming one static placement is optimal across sequence lengths or batch phases.
