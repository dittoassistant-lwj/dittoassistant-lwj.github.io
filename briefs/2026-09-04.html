Most important paper of the day

BASP: Communication-Efficient Batch-Aware Sequence Parallelism for LLM Training

Authors & affiliations: Bigyan Ghimire and Jon C. Calhoun. Affiliation: Holcombe Department of Electrical and Computer Engineering, Clemson University, Clemson, USA.

Tags: Sequence Parallelism, Collective Communication, LLM Training

Why this is the top pick: This is the best signal today because it is directly about collective communication efficiency for long-context LLM training. The idea is simple but architecturally sharp: if a micro-batch contains independent sequences, the communication domain does not always need to be the full training group.

Deeper explanation: BASP’s core move is to stop treating sequence-parallel attention as requiring one full-world collective. For a micro-batch of B independent sequences on N GPUs, it forms B disjoint groups of K=N/B GPUs, so each sequence runs its all-to-all only within its group. The result is especially interesting for real clusters because K can be chosen to match locality boundaries: keep the collective inside an NVLink island when possible, and avoid turning long-context training into avoidable inter-node all-to-all traffic. The paper reports modest but real end-to-end gains, while claiming much larger reductions in all-to-all time in high micro-batch settings. For Ethan’s world, the key idea is not the specific implementation; it is exposing batch semantics to the collective planner.

  • Problem: Long-context LLM training uses sequence parallelism to fit activation memory, but Ulysses-style sequence parallelism performs one global all-to-all across all GPUs even when the micro-batch contains multiple independent sequences. That makes communication grow in a way the batch structure could have avoided.
  • Key contributions:
  • Introduces Batch-Aware Sequence Parallelism (BASP), which partitions GPUs into disjoint sequence-parallel groups according to micro-batch size instead of using one global N-way collective.
  • Reduces per-GPU all-to-all peers from N−1 to K−1 where K=N/B, allowing traffic to be localized to faster intra-node links when K matches GPUs per node.
  • Reports 1.17–1.31× end-to-end training-time improvement on Llama and Qwen models on an NVIDIA A100 cluster, with identical accuracy and memory usage to Ulysses-SP.
  • Why it matters architecturally: For long-context training stacks, feed micro-batch structure into the communication planner. If sequences are independent, form sequence-parallel subgroups that match physical locality boundaries, then compare global all-to-all versus multiple smaller concurrent all-to-alls under the actual NVLink/IB topology.
  • Useful diagram: Figures 2, 4, 5, and 6 are the useful architecture diagrams: they contrast Ulysses-SP’s global all-to-all with BASP’s disjoint GPU groups and show how the communication pattern shrinks. Figure 1 is also useful because it shows all-to-all taking an increasing share of iteration time as micro-batch size grows.

BASP: Communication-Efficient Batch-Aware Sequence Parallelism for LLM Training

Authors & affiliations: Bigyan Ghimire and Jon C. Calhoun. Affiliation: Holcombe Department of Electrical and Computer Engineering, Clemson University, Clemson, USA.

Tags: Sequence Parallelism, Collective Communication, LLM Training

Problem: Long-context LLM training uses sequence parallelism to fit activation memory, but Ulysses-style sequence parallelism performs one global all-to-all across all GPUs even when the micro-batch contains multiple independent sequences. That makes communication grow in a way the batch structure could have avoided.

Key contributions from the authors:

  • Introduces Batch-Aware Sequence Parallelism (BASP), which partitions GPUs into disjoint sequence-parallel groups according to micro-batch size instead of using one global N-way collective.
  • Reduces per-GPU all-to-all peers from N−1 to K−1 where K=N/B, allowing traffic to be localized to faster intra-node links when K matches GPUs per node.
  • Reports 1.17–1.31× end-to-end training-time improvement on Llama and Qwen models on an NVIDIA A100 cluster, with identical accuracy and memory usage to Ulysses-SP.

Why it matters: This is the best signal today because it is directly about collective communication efficiency for long-context LLM training. The idea is simple but architecturally sharp: if a micro-batch contains independent sequences, the communication domain does not always need to be the full training group.

Key insights:

  • The paper reframes all-to-all group size as a tunable topology/locality decision rather than a fixed consequence of sequence parallelism.
  • BASP is most attractive when group boundaries align with high-bandwidth local fabrics such as NVLink islands, avoiding unnecessary inter-node InfiniBand traffic.
  • The optimization preserves the sequence shard size and memory footprint, so the win comes from collective localization, not from changing the model or reducing context length.
  • The paper’s limit case is important: the method depends on useful divisibility between GPU count and micro-batch size, so production planners need fallback handling for awkward batch sizes.
  • This is a reminder that collective libraries should expose semantic structure from the workload, not just tensor shapes.

Actionable lessons: For long-context training stacks, feed micro-batch structure into the communication planner. If sequences are independent, form sequence-parallel subgroups that match physical locality boundaries, then compare global all-to-all versus multiple smaller concurrent all-to-alls under the actual NVLink/IB topology.

Useful diagram: Figures 2, 4, 5, and 6 are the useful architecture diagrams: they contrast Ulysses-SP’s global all-to-all with BASP’s disjoint GPU groups and show how the communication pattern shrinks. Figure 1 is also useful because it shows all-to-all taking an increasing share of iteration time as micro-batch size grows.

Every Kernel Is a Join: Automatic Multi-GPU Parallelism for AI Computations in Einsummable

Authors & affiliations: Zhimin Ding, Chen-Kuan Liao, Chima Adiole, Brianna Barrow, Fangzhou Du, Yu Hsiao, Ge Huang, Yicheng Jin, Ismail Syed, and Chris Jermaine. Affiliation: Rice University, Houston, USA.

Tags: Multi-GPU Parallelism, Communication Planning, AI Systems

Problem: Automatically distributing AI computations across GPUs is hard because each operator admits many possible sharding/decomposition choices, and a bad choice can make communication overhead exceed the compute speedup.

Key contributions from the authors:

  • Models AI operations as relational joins followed by aggregations over tensor relations, exposing valid decompositions through “join-agg specs.”
  • Uses a dynamic-programming optimizer to choose decompositions over the whole computation using a communication-cost proxy.
  • Synthesizes topology-aware exchange programs for decomposed operations, replacing a fixed menu of collectives with per-computation communication plans.
  • Reports that the automatic system outperforms hand-tuned PyTorch and vLLM on LLaMA transformer blocks on an eight-GPU A100 server in the authors’ evaluation.

Why it matters: This is not a network protocol paper, but it is very relevant to cluster software stacks because it treats communication planning as query optimization. That mental model is useful for future collective/runtime design: logical tensor programs should be separated from physical data movement plans.

Key insights:

  • The “every kernel is a join” abstraction creates a larger search space than named parallelism strategies like tensor, sequence, or data parallelism.
  • Exchange programs are the network-facing piece: the runtime synthesizes the movement graph required by a chosen decomposition instead of assuming pre-baked collective calls.
  • The cost model is communication-centric, which matches the reality that multi-GPU speedups often fail at the data-movement boundary.
  • The current evaluation is intra-server A100-scale, so extension to multi-node fabrics would need topology models for NICs, rails, congestion, and collective contention.

Actionable lessons: For AI runtime design, separate the semantic computation graph from the physical communication graph. A production version would need fabric-aware costs—NVLink versus PCIe versus NIC rails, message size regimes, and overlap behavior—rather than only operator-local decomposition rules.

Latency-Aware Orchestration for Multi-Agent LLM Workflows on Heterogeneous GPUs

Authors & affiliations: Jinghao Wang, Yifeng Zhang, Xiao Zhou, Yao Lu, Yihui Zhang, Xiaoyang Sun, Tianyu Wo, Xu Wang, Chunming Hu, and Renyu Yang. Affiliation: Beihang University, Beijing, China; University of Leeds, Leeds, United Kingdom.

Tags: LLM Serving, Heterogeneous GPUs, Runtime Orchestration

Problem: Multi-agent LLM workflows run over heterogeneous GPU pools where model residency, KV/prefix state, loading delays, and future dependencies matter. Request-only scheduling reacts too late and can waste scarce high-memory GPUs or repeatedly reload useful state.

Key contributions from the authors:

  • Constructs physical execution alternatives for concurrent multi-agent workflows, including same-deployment fusion and compatible model-lifecycle actions.
  • Uses prediction to estimate device-specific execution time, peak memory, model-load time, and readiness across workflow dependencies.
  • Schedules under live pool state and cumulative memory constraints, reranking uncommitted choices using runtime feedback.
  • Reports reductions in burst makespan and p95 completion latency versus Parrot and Kairos in the authors’ workload evaluation.

Why it matters: This is more serving-orchestration than network research, but it is still useful infrastructure signal. The interesting part is that it treats model availability and resident state as first-class scheduling objects, which is exactly where heterogeneous accelerator fleets become messy.

Key insights:

  • The paper’s central diagnosis is that model loading and reacquire waits can dominate user-visible latency, so placement decisions must look ahead across workflow edges.
  • Logical workflow semantics and physical execution units are separated; that lets the runtime fuse or reorder safe work without changing externally visible behavior.
  • Heterogeneity matters through both compute latency and memory feasibility—some activations are only viable on a subset of devices.
  • The system is adjacent to network-aware serving because resident-state movement and model lifecycle decisions define what must cross storage, host memory, or accelerator interconnects.

Actionable lessons: In heterogeneous inference clusters, schedule state lifetime, not just requests. Track model residency, KV/prefix reuse, load time, and memory headroom as coupled resources; otherwise the system optimizes GPU assignment while silently paying repeated data-movement and model-load taxes.

DynaNDE: Dynamic Near-Data Expert Scheduling for Batched MoE Inference

Authors & affiliations: Xiaoyang Lu, Belthangady Akash Vi Narayana Pai, and Xian-He Sun. Affiliation: Illinois Institute of Technology, Chicago, Illinois, USA.

Tags: MoE Inference, Near-Data Processing, Heterogeneous Accelerators

Problem: MoE inference on accelerator systems suffers from expert-parameter movement: many experts cannot all reside in accelerator memory, so fetching selected experts from external memory stalls execution. Near-data processing can help, but scheduling must account for hardware heterogeneity, expert concurrency, and temporal reuse.

Key contributions from the authors:

  • Introduces DynaNDE, a dynamic expert scheduler for cooperative NPU/NDP MoE inference.
  • Builds an analytical model covering hardware heterogeneity, parameter transfers, activation movement, and communication-computation overlap.
  • Accounts for expert-level concurrency in batched inference and reuses experts already resident in NPU memory to avoid redundant parameter movement.
  • Reports average speedups of 2.6× for prefill and 2.2× for decoding versus the MoNDE NPU-NDP baseline.

Why it matters: This is relevant because it attacks the movement wall inside MoE inference. Even though the paper frames “NPU” generically, the architecture question maps cleanly to GPU/NPU/near-memory designs: should we move expert weights to compute, activations to near-memory compute, or exploit reuse and overlap dynamically?

Key insights:

  • The paper separates PMove, moving expert parameters to the accelerator, from AMove, moving activations toward near-data compute; that is the core data-movement trade-off.
  • Batching creates expert-level concurrency that a static offload policy misses; hot experts and concurrent token groups change the best placement per layer.
  • Temporal expert reuse turns accelerator memory into a small expert cache, so scheduling and caching should be co-designed.
  • The result is a smaller-scale analogue of cluster MoE routing: minimize heavy state movement, move lighter activations when possible, and exploit locality windows.

Actionable lessons: For MoE serving architecture, measure weight movement, activation movement, and reuse windows separately. A good scheduler should decide per layer and per batch whether to execute experts near memory or on the accelerator, and it should preserve hot experts in fast memory when reuse is likely.

Multi-Turn LLM Conversations under the Least-Recently-Used Policy: Mean-Field Asymptotics and Hit Ratio Approximation

Authors & affiliations: Heyuan Yao, Chutong Gao, Yuan Lyu, Izzy Grosof, and David Simchi-Levi. Affiliation: Northwestern University, Evanston, IL, USA; Purdue University, West Lafayette, IN, USA; HKUST, Hong Kong SAR.

Tags: KV Cache, LLM Serving, Capacity Planning

Problem: Multi-turn LLM serving depends heavily on KV cache hit ratio, but conversations grow over turns and compete for finite HBM under eviction. Operators need a way to estimate cache hit ratio without relying only on expensive trace simulation.

Key contributions from the authors:

  • Formulates a multi-turn conversation model for LLM serving under whole-content LRU eviction.
  • Proves mean-field convergence of the hit ratio as arrival rate and HBM capacity scale proportionally.
  • Derives a practical hit-ratio estimator and validates it using Qwen3-8B serving experiments on Ascend 910B2 NPUs with ShareGPT conversations.

Why it matters: This is a softer network pick, but it matters for disaggregated serving because KV-cache residency controls what must be recomputed, transferred, or spilled. Better HBM sizing models reduce surprise traffic on the prefill/decode and memory paths.

Key insights:

  • The useful abstraction is the tagged-conversation displacement process: eviction is modeled by the cumulative KV-block mass inserted or refreshed ahead of a conversation.
  • For prefill-decode disaggregation, response KV write-back behavior changes the residency dynamics; that matters when comparing systems.
  • The estimator can support capacity planning before full deployment traces exist, but its assumptions should be checked against real multi-tenant workload skew.
  • Cache hit ratio should be treated as a system-level performance primitive, not merely an application metric.

Actionable lessons: When sizing serving pools, model KV cache residency as a stochastic workload with turn growth and finite HBM, then translate misses into recompute, transfer, and spill costs. For disaggregated systems, explicitly model whether response KV is written back to prefill-side workers or reconstructed later.
