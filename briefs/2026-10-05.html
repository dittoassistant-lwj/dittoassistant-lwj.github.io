HetCCL: Accelerating LLM Training with Heterogeneous GPUs

Authors & affiliations: Heehoon Kim, Jaehwan Lee, Taejeoung Kim, Jongwon Park, Jinpyo Kim, Pyongwon Suh, Ryan H. Choi, Sangwoo Lee, and Jaejin Lee — Moreh Inc.; Department of Computer Science and Engineering, Seoul National University; Samsung Research; Graduate School of Data Science, Seoul National University.

Tags: Collective Communication, Heterogeneous GPU Clusters, RDMA

Problem: Large LLM training clusters increasingly mix NVIDIA and AMD GPUs, but today’s training stacks bind collectives to vendor-specific libraries such as NCCL or RCCL. That makes cross-vendor data/model parallelism awkward or impossible, especially when the fast path needs RDMA rather than host-staged copies.

Key contributions from the authors:

  • Builds HetCCL, a cross-vendor collective communication library for training and inference on mixed NVIDIA/AMD GPU clusters.
  • Shows direct point-to-point RDMA between different vendors’ GPU memory without requiring driver modifications.
  • Wraps vendor-optimized NCCL/RCCL operations into a unified framework and evaluates LLM training on a multi-vendor GPU cluster, reporting homogeneous performance comparable to NCCL/RCCL while enabling heterogeneous scaling.

Why it matters: This is today’s most directly useful paper for heterogeneous AI infrastructure. It treats cross-vendor collectives as a systems/networking problem, not just a framework API problem: GPU memory registration, RDMA path selection, and backend interop all have to line up before “use all available accelerators” becomes real.

Key insights:

  • Cross-vendor GPU training is blocked less by compute compatibility than by the collective layer and its assumptions about vendor-homogeneous GPU memory and transport paths.
  • RDMA is the key escape hatch: avoiding CPU staging is what makes mixed-vendor multi-node training plausible instead of a slow compatibility mode.
  • A practical hetero-CCL needs to preserve optimized vendor libraries for intra-vendor paths rather than replacing NCCL/RCCL with a lowest-common-denominator stack.
  • The paper’s design suggests heterogeneity support should live below PyTorch-level training code, so applications do not need to be rewritten when the cluster inventory changes.

Actionable lessons: For mixed GPU/NPU fleets, keep the collective interface stable and make transport/backend selection a runtime concern. Validate direct memory registration, RDMA reachability, and fallback paths independently; a hetero cluster that silently falls back to host staging can look “functional” while destroying MFU.

Zorse: Optimizing LLM Training Efficiency on Heterogeneous GPU Clusters

Authors & affiliations: Runsheng Benson Guo, Utkarsh Anand, Khuzaima Daudjee, and Rathijit Sen — University of Waterloo; Microsoft.

Tags: Heterogeneous GPU Clusters, Distributed Training, Parallelism Planning

Problem: Homogeneous clusters are increasingly unrealistic for many teams, but heterogeneous GPU pools create mismatched compute, memory, and interconnect constraints. Standard tensor/data/pipeline parallel choices either assume uniform devices or communicate too aggressively over slow links.

Key contributions from the authors:

  • Characterizes why tensor parallelism is often unattractive in low/mid-tier heterogeneous clusters because of frequent communication over limited interconnects.
  • Builds Zorse, a system that integrates pipeline parallelism and data parallelism with asymmetric stages and heterogeneous data-parallel groups.
  • Adds a planner that automatically searches training configurations and reports up to 3× higher throughput on representative heterogeneous clusters for models up to 65B parameters.

Why it matters: Zorse is useful because it puts network diversity into the parallelism decision. The key point is not merely “some GPUs are slower”; it is that different links make different forms of parallelism viable, and the planner has to know when to avoid communication-heavy tensor parallelism.

Key insights:

  • Heterogeneous training is often a slow-link problem disguised as a GPU scheduling problem.
  • Pipeline parallelism can absorb heterogeneity better than tensor parallelism when cross-device bandwidth is weak or uneven.
  • Asymmetric pipeline stages are not just a load-balancing trick; they are a way to match stage width to both memory capacity and communication cost.
  • A planner for real clusters should model devices, memory, and network classes together rather than optimizing each axis independently.

Actionable lessons: When building planners for mixed accelerator fleets, first classify links by whether they can support frequent intra-layer collectives. Use tensor parallelism only inside high-bandwidth islands, then use pipeline/data parallelism to bridge weaker network domains.

Useful diagram: Figure 1 compares hardware FLOPS utilization for tensor parallelism versus ZeRO-style data parallelism across AWS GPU VM types. The useful signal is that TP only looks competitive on the high-bandwidth A100 setup, reinforcing the link-aware planning argument.

ByteScale: Efficient Scaling of LLM Training with a 2048K Context Length on More Than 12,000 GPUs

Authors & affiliations: Hao Ge, Junda Feng, Qi Huang, Fangcheng Fu, Xiaonan Nie, Lei Zuo, Haibin Lin, Bin Cui, and Xin Liu — Peking University; ByteDance Seed.

Tags: Long-Context Training, Dynamic Communication Groups, GPU Clusters

Problem: Long-context LLM training mixes very long and short sequences, but static DP/CP meshes force redundant communication and imbalanced compute. The result is wasted bandwidth for short sequences and idle devices for length-skewed batches.

Key contributions from the authors:

  • Proposes Hybrid Data Parallelism (HDP), unifying inter-data DP and intra-data context parallelism so sequences can use a variable number of devices.
  • Introduces data-aware sharding, dynamic communication groups for short sequences, and selective offloading to reduce communication for long sequences.
  • Adds a balance scheduler and evaluates models from 7B to 141B with 256K–2048K context lengths on a production cluster of more than 12,000 GPUs, reporting up to 7.89× speedup over existing approaches.

Why it matters: This is a cluster-scale communication-efficiency paper hiding inside long-context training. The important bit for Ethan is the dynamic communication-group design: the network should not pay for a full static mesh when the current sequence only needs a subset of devices.

Key insights:

  • Static 2D meshes are a poor fit when sequence lengths vary widely; the communication group should follow the data shape.
  • Short sequences need communication elimination, while long sequences need communication compression/offloading — one policy does not cover both regimes.
  • Load balance must account for attention’s sequence-length-dependent compute, not just token count.
  • At 12k+ GPU scale, modest per-sequence overcommunication becomes a first-order cluster efficiency problem.

Actionable lessons: For long-context training, expose sequence length and sharding degree to the communication planner. Build collectives over minimal dynamic groups when possible, and test whether your “balanced” token partition is actually balanced in attention compute time.

Hiding Communication Cost in Distributed LLM Training via Micro-batch Co-execution

Authors & affiliations: Haiquan Wang, Chaoyi Ruan, Jia He, Jiaqi Ruan, Chengjie Tang, Xiaosong Ma, and Cheng Li — University of Science and Technology of China; Mohamed bin Zayed University of Artificial Intelligence; Shanxi University.

Tags: Communication/Computation Overlap, Distributed Training, GPU Runtime

Problem: Distributed LLM training loses MFU to intra-layer communication from tensor, sequence, context, and expert parallelism. Existing overlap techniques either split optimized operators too aggressively or do not generalize cleanly across parallelism modes.

Key contributions from the authors:

  • Introduces DHelix, a strand-interleaving micro-structure that co-executes forward and backward work from two micro-batch streams.
  • Uses operator-level overlap profiling plus dynamic-programming search to pair compute-heavy and communication-heavy operators across strands.
  • Shares model states and activation space with under 3% extra memory, integrates with data/model/pipeline parallelism, and reports 12–40% improvement on 64×A40 and 2–29% on 64×A800 clusters.

Why it matters: DHelix is relevant because it treats communication overlap as a runtime scheduling problem at operator granularity, with separate CUDA streams for computation, local-node communication, and cross-node communication. That maps well to the practical pain of making collectives disappear under useful work rather than merely moving them around.

Key insights:

  • Communication overlap needs complementary work; pairing arbitrary operators is not enough if dependencies or memory lifetimes conflict.
  • Local-node and cross-node communication should be modeled separately because they contend with different resources and expose different overlap opportunities.
  • The faster H100 network reduces the gain, which is a useful sanity check: overlap tricks matter most where communication remains exposed.
  • Memory sharing is what makes two-strand co-execution feasible; otherwise overlap would trade bandwidth stalls for capacity stalls.

Actionable lessons: Profile operators by overlap behavior, not just standalone latency. For training runtimes, keep local fabric, cross-node fabric, and compute streams explicit in the scheduler, and verify gains separately on slower Ethernet/IB clusters versus high-end scale-up domains.
